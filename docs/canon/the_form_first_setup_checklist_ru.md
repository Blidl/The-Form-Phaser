# The Form — First Setup Checklist (RU, Phaser)

## Назначение документа

Этот документ фиксирует **самые первые практические шаги** по созданию нового прототипа `The Form` в `Phaser` в соответствии с принятым каноном:

- `Phaser-native`
- `docs-first`
- `Codex-first`
- `scene-first`
- `TypeScript-first`
- один `pf_player` с тремя формами внутри: `Ball / Triangle / Square`
- стартовая рабочая сцена: `sc_test`
- физическая модель: `custom platformer`, а не full physics-sim driven prototype

Документ не описывает полную реализацию механик.
Его цель — помочь **правильно собрать каркас проекта и репозитория**, чтобы дальше двигаться без хаоса.

---

## Что должно получиться в конце этого чеклиста

После выполнения чеклиста у проекта должен появиться:

- чистый новый Phaser-проект с базовой структурой папок;
- стартовые сцены `sc_bootstrap` и `sc_test`;
- каркас `pf_player`;
- каркас камеры;
- базовые world-модули;
- базовый UI-shell;
- placeholder-ассеты;
- `sc_test`, в которой можно запустить игру и увидеть, что проект собран правильно;
- docs-layer, на который потом можно ссылаться в prompt для Codex.

На этом этапе **механики ещё не обязаны быть реализованы полностью**.
Главное — собрать правильную основу.

---

## Общие правила выполнения

Перед началом:

1. Не пытаться сразу делать `Triangle`, `Square rollover`, `trail` и сложную геометрию.
2. Не собирать god-object / god-script архитектуру.
3. Не делать три разных player-базы как основу.
4. Сразу держать структуру удобной для коротких Codex prompt.
5. Все временные ассеты допустимы как placeholder.
6. Имена ресурсов сразу держать чистыми и единообразными.

---

## Этап 1. Создать новый проект

### Шаг 1.1
Создать новый проект `Phaser`.

Рекомендуемое имя:
- `TheForm_Prototype`

Рекомендуемая техническая база:
- `TypeScript` как основной язык проекта;
- стандартный Phaser lifecycle;
- минимальный стартовый шаблон без лишней framework-надстройки.

### Шаг 1.2
Сразу сохранить проект в отдельной чистой папке/репозитории.

### Шаг 1.3
Сразу определить техническую рамку:
- gameplay остаётся side-view / planar;
- прототип не строится вокруг полноценных physics-sim chain взаимодействий;
- дальнейшая логика движется как custom platformer.

### Критерий успеха
- проект открывается без legacy-хвостов;
- базовый pipeline понятен с самого начала;
- выбранная стартовая структура не тащит ненужную тяжёлую обвязку.

## Этап 2. Собрать базовую структуру папок

Создать верхнеуровневые группы:

- `assets/sprites`
- `assets/audio`
- `assets/fx`
- `assets/data`
- `assets/tilemaps` (опционально)
- `src/scenes`
- `src/game`
- `src/ui`
- `src/debug`
- `src/config`
- `src/shared`
- `docs/canon`
- `docs/prompts`
- `docs/acceptance`

Внутри них создать подгруппы.

### Для `assets/sprites`
- `player`
- `ui`
- `world`
- `debug`
- `fx`

### Для `src/game`
- `core`
- `player`
- `forms`
- `world`
- `camera`
- `interactions`

### Для `src/scenes`
- `BootScene.ts`
- `TestScene.ts`

### Для `assets/data`
- `config`
- `tuning`
- `levels`

### Критерий успеха
- проект визуально организован;
- уже на старте понятно, куда пойдёт каждый новый ресурс;
- структура понятна и человеку, и Codex.

---

## Этап 3. Создать placeholder-спрайты

На этом этапе не нужен красивый арт.
Нужны **понятные временные формы**.

### Создать:
- `spr_ball_placeholder`
- `spr_triangle_placeholder`
- `spr_square_placeholder`
- `spr_marker_placeholder`
- `spr_platform_placeholder`
- `spr_breakable_placeholder`
- `spr_checkpoint_placeholder`
- `spr_hazard_placeholder`
- `spr_ui_form_ball`
- `spr_ui_form_triangle`
- `spr_ui_form_square`
- `spr_ui_charge_segment`
- `spr_ui_trail_segment`

### Требования к placeholder-формам

#### Ball
- простой круг;
- origin по центру.

#### Triangle
- простой читаемый треугольник;
- origin по центру;
- форма должна быть легко читаема по направлению вершины.

#### Square
- простой квадрат;
- origin по центру.

#### Marker
- маленький заметный маркер;
- должен быть видим поверх формы.

### Критерий успеха
- у трёх форм есть простая визуальная база;
- marker можно будет показывать поверх игрока;
- UI-иконки можно использовать без финального арта.

---

## Этап 4. Создать сцены

### Шаг 4.1 — `sc_bootstrap`
Создать `BootScene.ts` с ключом сцены `sc_bootstrap`.

Назначение:
- минимальная стартовая сцена проекта;
- preload базовых ассетов;
- запуск `sc_test`.

### Шаг 4.2 — `sc_test`
Создать `TestScene.ts` с ключом сцены `sc_test`.

Назначение:
- главная test scene для проверки прототипа;
- именно в ней позже будут собираться все тестовые зоны.

### Критерий успеха
- проект запускается в понятную стартовую сцену;
- `sc_test` существует как основная рабочая сцена.

---

## Этап 5. Создать базовые core-модули

### Создать:
- `pf_bootstrap`
- `pf_player`
- `pf_camera_controller`
- `pf_ui_root`
- `pf_debug_controller`

### Назначение

#### `pf_bootstrap`
- минимальный стартовый управляющий слой;
- preload / scene start.

#### `pf_player`
- единственный основной player module;
- внутри него позже живут формы `Ball / Triangle / Square`.

#### `pf_camera_controller`
- отдельный контроллер камеры;
- не смешивать с логикой игрока.

#### `pf_ui_root`
- отдельный корень UI.

#### `pf_debug_controller`
- отдельный debug-layer объект;
- не тащить debug-логику в player больше, чем нужно.

### Критерий успеха
- существует clean shell для главных систем;
- структура сразу разделяет ответственность по сущностям.

---

## Этап 6. Создать world-модули

Создать базовые сущности мира:

- `pf_solid_block`
- `pf_slope_block`
- `pf_breakable_block`
- `pf_checkpoint`
- `pf_hazard`
- `pf_moving_platform`
- `pf_trigger_platform`
- `pf_wind_zone`

### Базовые принципы
- все world-объекты должны быть отдельными;
- не пытаться делать “универсальный суперкласс всего мира”;
- placeholder-поведение допустимо;
- пока достаточно каркасов.

### Критерий успеха
- все обязательные элементы test scene имеют собственные точки сборки.

---

## Этап 7. Назначить placeholder-визуал и origin

Для всех созданных сущностей назначить временные sprites, где это уместно.

Особенно важно:

### `pf_player`
На старте можно временно назначить один placeholder-sprite, например `spr_ball_placeholder`.

### Для world-модулей
Назначить простые временные sprites, чтобы сцена сразу читалась глазами.

### Критерий успеха
- проект уже визуально различим;
- видно игрока, платформы и ключевые world-объекты.

---

## Этап 8. Настроить базовые collision-слои

Определить минимальный collision contract:

- что считается solid surface;
- что считается slope surface;
- что считается hazard;
- что считается checkpoint/trigger;
- где будут attach-compatible поверхности для `Square`.

На старте достаточно даже очень простого представления, если оно не ломает дальнейшее расширение.

### Критерий успеха
- есть ясная договорённость о world categories;
- будущие feature-slice не будут изобретать collision taxonomy заново.

---

## Этап 9. Собрать каркас `pf_player`

`pf_player` пока не обязан содержать финальную механику.

На этом шаге он должен иметь:

- transform / position shell;
- placeholder visual;
- current form state;
- marker shell;
- базовый runtime state;
- точку входа для input;
- точку входа для form switching.

### Критерий успеха
- есть один единый player-root;
- формы пока могут быть не реализованы полностью, но архитектурная точка входа уже задана.

---

## Этап 10. Собрать каркас камеры

Создать минимальный `pf_camera_controller`.

На старте достаточно:

- camera follow target;
- базового frame / deadzone placeholder;
- lower-center bias skeleton, если он нужен уже на этом этапе;
- shell для будущего tuning.

### Критерий успеха
- камера уже не смешана с player-core;
- её можно развивать отдельно.

---

## Этап 11. Собрать минимальный UI-shell

Создать `pf_ui_root`, который пока может быть очень простым.

На старте желательно иметь:

- current form indicator placeholder;
- next form indicator placeholder;
- место под charges/trail UI;
- место под debug text, если это удобно.

### Критерий успеха
- UI-слой существует отдельно;
- будущие form / charges / trail фичи есть куда подключать.

---

## Этап 12. Собрать `sc_test`

Разместить в `sc_test` минимум:

- player spawn;
- несколько плоских платформ;
- хотя бы один slope;
- hazard;
- checkpoint;
- moving platform placeholder;
- trigger platform placeholder;
- wind zone placeholder;
- место под будущие test sections.

### Критерий успеха
- test scene уже похожа на полигон, а не на пустой экран;
- видно, что проект собран в рабочую основу.

---

## Этап 13. Проверить play loop

Нужно проверить:

- проект стартует;
- assets грузятся;
- сцены переключаются как ожидается;
- игрок появляется;
- камера работает хотя бы в минимальном режиме;
- ничего не развалено в базовой структуре.

### Критерий успеха
- можно запустить проект и пройти первый smoke test без ручного хака каждого шага.

---

## Этап 14. Подключить документацию как reference layer

Внутри проекта или рядом с ним нужно подготовить docs-layer так, чтобы дальше можно было удобно собирать prompt для Codex.

Минимально нужны:

- актуальные канонические md-файлы;
- понятные пути к ним;
- папка `docs/prompts` для будущих feature prompt;
- договорённость, что новый slice опирается только на релевантные документы.

### Критерий успеха
- документация готова стать реальным источником prompt-контекста, а не просто лежать мёртвым архивом.

После выполнения этого чеклиста у проекта есть:

- чистая стартовая Phaser-основа;
- канонические сцены;
- каркас игрока;
- каркас камеры;
- каркас UI;
- каркас world-объектов;

- `sc_test` как главная среда проверки;
