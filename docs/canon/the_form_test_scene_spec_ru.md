# The Form — Test Scene Spec (RU)

## Статус документа
Canonical draft для нового прототипа `The Form`.

Этот документ фиксирует состав, назначение и правила использования **канонической test scene** для первого прототипа.

---

## 1. Назначение test scene

`test scene` — это не уровень кампании и не вертикальный срез с началом и концом.
Это **каноническая среда проверки механик**, в которой должны проверяться:

- базовое движение игрока;
- form switching;
- поведение `Ball`;
- поведение `Triangle`;
- поведение `Square`;
- взаимодействие форм с поверхностями;
- взаимодействие с `wind`, `hazard`, `checkpoint`;
- взаимодействие с `moving platform` и `trigger platform`;
- работа UI и marker в условиях реального теста.

Первая playable-сборка прототипа должна быть ориентирована именно на эту scene.

---

## 2. Общие принципы test scene

### 2.1. Главный принцип
Scene должна быть построена не как красивая сцена, а как **ясный набор испытательных секций**.

### 2.2. Читаемость важнее декора
На первом прототипе не требуется декоративное оформление.
Главная задача — чтобы было легко понять:

- где проверяется каждая механика;
- откуда начинать тест;
- где ожидается корректное поведение;
- где произошёл сбой.

### 2.3. Один scene — много секций
Первая версия использует **одну test scene**, в которой собраны все обязательные тестовые зоны.

### 2.4. Минимум лишнего шума
В test scene не должно быть:

- сюжетных объектов;
- лишнего UI;
- декоративных анимаций, которые мешают считывать механику;
- неоправданных сложных scripted events.

---

## 3. Канонический состав test scene

В первой канонической версии test scene должны присутствовать все перечисленные ниже зоны.

### 3.1. Стартовая безопасная площадка
Назначение:

- спавн игрока;
- первичная проверка движения;
- первичная проверка form switching;
- первичная проверка marker и UI.

Требования:

- ровная горизонтальная поверхность;
- достаточно свободного места слева и справа;
- отсутствие hazards в непосредственной близости;
- игрок стартует в форме `Ball`.

### 3.2. Секция обычного движения
Назначение:

- проверить разгон / торможение / air control;
- проверить обычный jump;
- проверить `coyote time`;
- проверить `input buffer`;
- проверить dynamic jump height у `Ball` и `Square`;
- проверить, что набор скорости в начале движения ощущается как инерционный, а не мгновенный;
- проверить, что остановка не обрубает скорость моментально (инерционное замедление);
- проверить различия feel движения между `Ball`, `Triangle`, `Square` по их отдельным параметрам.

Требования:

- длинный ровный пол;
- небольшой разрыв между платформами;
- несколько разных по длине платформ.

### 3.3. Секция Ball wall-bounce
Назначение:

- проверить rebound от стен;
- проверить fallback «нормаль + слабая поправка вверх» при слабой/нулевой входящей скорости;
- проверить reflection от нормали стены при выраженной входящей скорости в стену;
- проверить rebound chain;
- проверить hit pause при успешном rebound;
- проверить, что игрок может забираться наверх между узкими стенами;
- проверить, что wall rebound не требует ввода в сторону стены;
- проверить, что wall rebound не требует стартовой скорости в сторону стены;
- проверить minimum exit strength (не ниже обычного jump baseline);
- проверить приоритет coyote jump над wall rebound;
- проверить, что wall rebound валиден только от платформенных поверхностей.

Требования:

- минимум один узкий вертикальный колодец между двумя стенами;
- одна широкая вертикальная стена для одиночного bounce-теста;
- безопасная зона для повторных попыток.

### 3.4. Секция Ball floor/ceiling rebound
Назначение:

- проверить rebound от пола;
- проверить rebound от потолка;
- проверить reflection от потолка по текущему вектору скорости;
- проверить minimum exit strength для ceiling rebound;
- проверить вторую высоту rebound-chain.

Требования:

- участок пола и низкий потолок;
- геометрия, позволяющая многократно проверять rebound вверх-вниз.

### 3.5. Секция Triangle jump / freeze / dash
Назначение:

- проверить особый jump треугольника;
- проверить freeze по повторному нажатию `Jump` в воздухе;
- проверить поворот по направлению ввода;
- проверить dash по `Ability`;
- проверить dash с земли;
- проверить dash из воздуха через freeze;
- проверить dash из воздуха без freeze.

Требования:

- открытое пространство для воздушных манёвров;
- несколько удобных поверхностей для старта dash;
- достаточный обзор траектории.

### 3.6. Секция Triangle breakable test
Назначение:

- проверить разрушение `breakable`-объектов только через dash треугольника;
- проверить, что после разрушения область становится проходимой;
- проверить, что `Ball` и `Square` не ломают такие объекты;
- проверить поведение при прохождении через несколько breakable-поверхностей подряд.

Требования:

- минимум одна одиночная breakable-стенка;
- минимум одна последовательность из нескольких breakable-объектов.

### 3.7. Секция Triangle non-breakable impact
Назначение:

- проверить, что при ударе в непробиваемую поверхность треугольник застревает углом;
- проверить, что по `Jump` он отпрыгивает по нормали поверхности;
- проверить, что потом он приходит в устойчивое положение на грань, а не остаётся на углу.

Требования:

- непробиваемая стена;
- безопасная геометрия для повторных попыток.

### 3.8. Секция Square attach basics
Назначение:

- проверить attach к полу;
- проверить attach к стенам;
- проверить attach к потолку;
- проверить attach к наклонным поверхностям;
- проверить расход trail-ресурса по дистанции.

Требования:

- одна горизонтальная поверхность;
- одна вертикальная стена;
- один потолок, пригодный для attach;
- минимум один slope.

### 3.9. Секция Square trail behavior
Назначение:

- проверить, что при attach trail строится по валидной поверхности;
- проверить attach к уже существующему trail;
- проверить остановку trail-регена при начале нового attach;
- проверить авто-реген вне attach;
- проверить, что на уже существующем trail progress bar не тратится повторно;
- проверить attach к уже существующему trail даже при пустом progress bar;
- проверить повторный вход в attach на уже существующем trail при пустом progress bar после предварительного detach;
- проверить, что attach к поверхности без trail не происходит при пустом progress bar;
- проверить ручной regen по жесту `K + ввод в поверхность` в состоянии покоя;
- проверить, что для пола этот жест читается как `K + S` без `A / D`;
- проверить ручной regen и на уже существующем trail, и без trail под квадратом;
- проверить, что реген идёт от старого к новому.

Требования:

- достаточно длинные attach-compatible поверхности;
- понятная визуальная зона считывания trail.

### 3.10. Секция Square attach-jump
Назначение:

- проверить attach-jump по `Jump` при удержании attach;
- проверить уменьшенный фиксированный прыжок перпендикулярно поверхности;
- проверить возврат по «резинке» обратно к trail;
- проверить, что при отпускании attach квадрат отцепляется и падает.
- проверить визуализацию «резинки»;
- проверить сценарий, где attach-jump тянет тяжёлый box-объект.
- проверить, что после возврата по резинке Square снова входит в attach на существующем trail даже при пустом progress bar.

Требования:

- минимум одна поверхность для attach-jump без подвижных объектов;
- свободное пространство рядом с поверхностью.

### 3.11. Секция Square rollover
Назначение:

- проверить rollover через внешний угол;
- проверить preview/start contract rollover;
- проверить успешный переход на новую поверхность;
- проверить возврат по обратной траектории, если attach на новой поверхности невозможен;
- проверить автоматический старт rollover без отдельной кнопки;
- проверить `TL / TR / BL / BR` corner-зоны и pivot contract;
- проверить бесшовный attach после успешного rollover.

Требования:

- минимум один чистый внешний угол floor→wall;
- минимум один чистый внешний угол wall→ceiling;
- минимум одна ситуация, где rollover валиден частично, но завершение attach должно провалиться и квадрат обязан вернуться назад.

Дополнительный канон секции:

- в текущем scope проверяется только `external-corner rollover`;
- внутренние углы в этой acceptance-зоне не обязательны;
- rollback-case должен позволять проверить возврат ровно по обратной траектории без дрейфа.

### 3.12. Секция hazards
Назначение:

- проверить death pause;
- проверить teleport на checkpoint;
- проверить полный reset состояния игрока;
- проверить, что следы / состояния / ресурсы сбрасываются корректно.

Требования:

- минимум одна hazard-зона;
- безопасная позиция checkpoint перед ней.

### 3.13. Секция checkpoint
Назначение:

- проверить активацию checkpoint;
- проверить respawn именно в сохранённой позиции;
- проверить respawn в дефолтной форме `Ball`.

Требования:

- минимум один checkpoint в середине scene;
- желательно ещё один checkpoint глубже по комнате для повторной проверки.

### 3.14. Секция wind zone
Назначение:

- проверить влияние ветра на все формы;
- проверить, что `Ball` сдувает сильнее всего;
- проверить, что `Triangle` сдувает средне;
- проверить, что `Square` сдувает слабее всего;
- проверить, что `Square` в attach ветром не сдувается;
- проверить, что wind меняет траекторию прыжка и падения;
- проверить замедление dash у Triangle.

Требования:

- отдельная wind zone в читаемой секции;
- достаточно пространства для входа и выхода из зоны ветра.

### 3.15. Секция moving platform
Назначение:

- проверить, что игрок корректно ездит на moving platform;
- проверить взаимодействие всех форм с движущейся опорой;
- проверить attach квадратом к moving platform;
- проверить trail на движущейся платформе.

Требования:

- минимум одна автоматически движущаяся платформа;
- траектория должна быть простой и читаемой.

### 3.16. Секция trigger platform
Назначение:

- проверить платформу, которая начинает движение по триггеру;
- проверить взаимодействие игрока с ней после активации;
- проверить attach и trail, если такая платформа attach-compatible.
- проверить, что до активации trigger platform не участвует в attach для Square.

Требования:

- минимум одна trigger platform;
- должен существовать понятный способ её активации.

### 3.17. Секция drag box
Назначение:

- проверить тяжёлый объект, который может активировать trigger вместо игрока;
- проверить, что Square может attach'иться к нему как к attach-compatible объекту;
- проверить, что тянуть его может только Square attach-jump;
- проверить, что Ball и Triangle читают его как твёрдое препятствие;
- проверить собственную гравитацию объекта и устойчивый контакт с полом.

Требования:

- минимум один `drag box`;
- минимум один trigger, который активируется именно этим box-объектом;
- достаточно места для attach-jump и подтягивания box к trigger-зоне.

## 4. Обязательные сценарии проверки

В первой test scene обязательно должны быть сценарии, где можно проверить:

### 4.1. Общие
- старт игрока в форме `Ball`;
- form switching `Q/E`;
- marker;
- UI;
- checkpoint;
- death / respawn.

### 4.2. Ball
- boost на земле;
- обычный jump;
- rebound от стены;
- rebound от потолка;
- rebound от пола;
- rebound chain;
- wall assist вверх;
- wall rebound без обязательного ввода в стену;
- wall rebound без обязательной стартовой скорости в стену;
- приоритет coyote jump над wall rebound;
- rebound только от платформенных поверхностей;
- в boosted jump под `K` прирост идёт по горизонтальной скорости, а не по высоте;
- при удержании `K` в воздухе air-control для Ball резко ограничен;
- при `K` без `A/D` Ball не должен сдвигаться в сторону;
- если `K` уже удерживается, разгон должен стартовать сразу при появлении `A/D`;
- при `K` без `A/D` jump остаётся обычным вертикальным;
- в boost-mode Ball должен иметь утолщённую обводку как визуальный индикатор режима;
- boost должен иметь мощный стартовый импульс и плавный переход к обычной boosted скорости без резкого обрыва.

### 4.3. Triangle
- особый jump;
- freeze;
- dash с пола;
- dash из воздуха;
- dash из воздуха без freeze;
- пробивание breakable;
- застревание углом в непробиваемую поверхность;
- recovery через jump по нормали.

### 4.4. Square
- attach на разных поверхностях;
- attach к поверхности через небольшой зазор в пределах допустимого acquire range;
- attach к валидной поверхности при удержании `K` даже без directional input;
- бесшовный переход `floor -> wall` при удержании attach;
- бесшовный переход `wall -> ceiling` при удержании attach;
- построение trail;
- attach к уже существующему trail;
- повторный attach к уже существующему trail при пустом progress bar;
- расход trail;
- regen trail;
- attach-jump;
- attach-jump return с повторным attach при пустом progress bar;
- rollover;
- rollback при неуспешном rollover;
- attach к moving surface.

### 4.5. Мир
- wind interaction;
- hazard;
- moving platform;
- trigger platform.
- drag box как activator/obstacle.

## 5. Пространственная организация scene

### 5.1. Scene должна быть зонирована
Игрок должен интуитивно понимать, где расположена проверка каждой механики.

### 5.2. Предпочтительный порядок секций
Рекомендуемый порядок расположения:

1. стартовая площадка;
2. базовое движение;
3. Ball-секции;
4. Triangle-секции;
5. Square-секции;
6. wind;
7. moving / trigger platforms;
8. hazards / checkpoint-проверки.

Этот порядок не обязан быть единственным, но он удобен для первой итерации.

### 5.3. Возвратность
Scene должна позволять быстро повторять тесты без долгого бэктрекинга.

---

## 6. UI и debug в test scene

В test scene должны корректно читаться:

- текущая форма;
- формы на `Q/E`;
- ресурс `Triangle`;
- ресурс `Square`;
- marker;
- debug UI.

Для `Square` debug-contract в test scene должен уметь показывать:

- зоны `TL / TR / BL / BR`;
- attach-valid и dangling corner-zones;
- pivot rollover, когда он реально создан;
- реальную текущую orientation Square, а не только axis-aligned body.

Test scene — основная среда, где эти элементы проверяются в реальном игровом состоянии.

### 6.1. Runtime authoring
Для `sc_test` допускается локальный runtime edit mode, если он:

- помогает быстро переставлять тестовую геометрию и объекты;
- не становится источником истины вместо канонического config-слоя;
- не ломает baseline gameplay при выключенном edit mode.

Каноничнее, если все основные элементы test scene управляются из одного конфигурационного слоя, а runtime edit mode служит ускорением ручной настройки.

---

## 7. Что НЕ требуется от первой test scene

В первой канонической версии **не требуется**:

- start window;
- сюжетная логика;
- полноценный level flow;
- финальный арт;
- финальная анимационная система;
- полноценный звук;
- расширенный production UI.

## 9. Статус старых документов о стартовом окне и старой scene-структуре

Любые старые документы, где scene описывалась:

- как стартовое меню;
- как уровень с большим количеством UI-обвязки;
- как сцена под старую архитектуру;

не считаются источником истины для нового прототипа.
Они могут использоваться только как historical/reference layer.

---

## 10. Итоговый contract

Для первого прототипа должна существовать **одна каноническая test scene**, которая:

- содержит все обязательные секции;
- позволяет проверить весь минимальный gameplay loop;
- подтверждает работоспособность `Ball`, `Triangle`, `Square`;
- подтверждает form switching;
- подтверждает работу мира и систем;
- служит основной средой сборки и итеративной отладки Phaser-native прототипа.
