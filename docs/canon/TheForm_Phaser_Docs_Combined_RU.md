# The Form — Phaser Docs Pack (RU)

Этот пакет содержит переписанную документацию прототипа `The Form` под разработку в `Phaser`.

## Базовая рамка пакета
- `Phaser-native`
- `docs-first`
- `Codex-first`
- `scene-first`
- `TypeScript-first`
- маленькие атомарные runtime-модули вместо giant-file подхода
- один `pf_player` с тремя формами внутри: `Ball / Triangle / Square`
- `custom platformer`, а не physics-sim first prototype
- каноническая среда проверки: `sc_test`
- целевой workflow: `1 prompt -> 1 готовая feature slice` настолько часто, насколько это реально без потери качества
- prompt для Codex должен быть коротким и ссылаться только на релевантные документы, чтобы минимизировать расход токенов

## Что переписано
Пакет сохраняет структуру исходного набора документов, но адаптирует её под Phaser-термины и Phaser/Codex workflow:

- `Rooms` -> `Scenes`
- `Objects` -> `scene objects / prefab-by-code modules / factories`
- `obj_*`-слой -> `pf_* / controller_* / scene object`-слой
- `GML / DnD`-ориентация -> `Phaser Scene / TypeScript / config objects / small modules`-ориентация
- `GameMaker-native` -> `Phaser-native`
- `Unity editor / Inspector / Prefab wiring` -> `repo structure / scene config / factory wiring / typed config`
- `C# component` -> `TypeScript module / class / helper`

## Документы, специально переписанные заново как engine-heavy слой
- `the_form_phaser_project_structure_ru.md`
- `the_form_first_setup_checklist_ru.md`
- `the_form_prototype_phaser_native_implementation_principles_ru.md`
- `the_form_codex_feature_prompt_contract_ru.md`

Остальные документы сохранены максимально близко к исходному канону по смыслу, механическому контракту и порядку чтения, но переведены в Phaser-эквиваленты и Phaser/Codex vocabulary.

## Главный практический смысл пакета
Пакет должен позволять работать так:

1. Пользователь даёт мне задачу и нужный контекст.
2. Я читаю только релевантные документы из пакета.
3. Я собираю короткий, узкий prompt для Codex.
4. Codex меняет только нужный slice Phaser-проекта.
5. На выходе стремимся получать одну законченную фичу за один prompt без giant-context и без giant-file архитектуры.

# The Form — Prototype Concept

Статус: canonical draft  
Дата: 2026-03-25

## 1. Назначение документа
Этот документ фиксирует концепт нового прототипа `The Form` в чистом виде, без исторических хвостов старой документации.

Документ отвечает на вопросы:
- что именно является первым прототипом;
- какую игровую ценность он должен доказать;
- какой у него scope;
- какие игровые ощущения считаются обязательными.

Если более детальные feature-документы конфликтуют с этим документом, сначала проверяется `prototype_decisions`, затем этот `prototype_concept`, и только потом historical/reference-слой.

## 2. Цель первого прототипа
Приоритет целей первого прототипа:
1. собрать **вертикальный срез** с ощущением настоящей игры;
2. проверить, что **ядро механик ощущается правильно**;
3. технически подтвердить контракт форм и их взаимодействий.

Прототип не является «черновым набором разрозненных тестов». Он должен уже давать читаемое ощущение игрового процесса, даже если в нём пока только одна test scene.

## 3. Общая идея прототипа
`The Form` — это 2D custom platformer, в котором один персонаж может переключаться между тремя формами:
- `Ball`;
- `Triangle`;
- `Square`.

Каждая форма решает задачи движения по-своему:
- `Ball` — скорость, распрыгивание, отскоки и мобильность;
- `Triangle` — направленный импульс, ориентация, freeze/dash и пробитие специальных объектов;
- `Square` — attach к поверхностям, trail-resource, привязанные прыжки и rollover через внешние углы.

Ключевая ценность прототипа — не просто показать три формы, а доказать, что:
- между ними интересно переключаться;
- каждая форма ощущается уникальной;
- окружение поддерживает эти различия;
- игрок может читать логику управления и состояния формы без сложного интерфейса.

## 4. Игровой каркас первого прототипа
Первый прототип строится вокруг одной `test scene`, которая уже должна быть полноценной канонической площадкой проверки.

Внутри неё должны быть представлены:
- ровный пол;
- стены;
- потолок;
- наклонные поверхности;
- узкий колодец между двумя стенами для проверки wall-bounce мяча;
- внешний угол для `Square External-Corner Rollover`;
- breakable wall/object для Triangle;
- hazard;
- checkpoint;
- finish / exit;
- moving platform;
- trigger platform;
- wind zone.

То есть это не «пустая тестовая сцена», а минимальный вертикальный срез, на котором уже можно проверять все обязательные контракты форм.

## 5. Игровые столпы прототипа

### 5.1. Form switching как центральная ось
Прототип строится вокруг идеи, что один и тот же персонаж решает разные задачи через смену формы. Игрок не выбирает единственный стиль движения — он постоянно переключает mode of traversal.

Смена формы должна быть:
- быстрой;
- читаемой;
- тактически полезной;
- доступной с самого начала;
- встроенной в реальный platforming, а не существующей отдельно от него.

### 5.2. У каждой формы — своя физика ощущения
Формы должны отличаться не только правилом способности, но и тем, как ощущаются:
- у `Ball` важны разгон, rebound, hit pause и ритм распрыгивания;
- у `Triangle` важны ориентация, ведущий угол, dash и «укладывание на грань»;
- у `Square` важны контакт с поверхностью, построение trail, удержание attach и резиновое возвращение.

### 5.3. Читаемость через marker
Для всех форм обязательна общая видимая **точка приложения силы / энергии** (`visual marker`).

Она нужна не как декоративный элемент, а как системный читаемый интерфейс движения:
- показывает направление намерения игрока;
- поддерживает ориентацию Triangle;
- участвует в поведении форм;
- служит общей визуальной грамматикой управления.

### 5.4. Platforming first
Прототип в первую очередь остаётся platformer-игрой.

Это означает:
- обязательны `input buffer` и `coyote time`;
- обязателен `air control`;
- обычные прыжки должны ощущаться управляемыми;
- сложность форм не должна ломать базовую читаемость платформинга.

## 6. Формы — high level vision

### 6.1. Ball
`Ball` — дефолтная форма и форма респавна.

Его задача в прототипе:
- быть самой понятной стартовой формой;
- давать мобильность через разгон и rebound;
- поддерживать ритм распрыгивания между поверхностями;
- чувствоваться самой «лёгкой» формой в wind interaction.

### 6.2. Triangle
`Triangle` — форма, где важнее всего ориентация.

Его задача в прототипе:
- показать, что повёрнутая форма реально меняет геймплей;
- дать игроку freeze/dash-модель позиционирования;
- работать с ведущим углом;
- разрушать специальные объекты, открывая путь дальше.

### 6.3. Square
`Square` — форма контакта, цепляния и управляемого перемещения вдоль поверхностей.

Его задача в прототипе:
- доказать attach-механику как самостоятельный столп;
- показать trail-resource как уникальную модель ресурса;
- дать rollover через внешний угол уже в первой playable-версии;
- показать привязанный attach-jump с возвратом.

## 7. Структура игрового цикла в test scene
Минимальный цикл прототипа:
1. spawn как `Ball`;
2. движение и прыжки;
3. переключение между формами `Q/E`;
4. использование уникальных способностей форм;
5. взаимодействие с поверхностями и объектами мира;
6. death/hazard -> checkpoint reset;
7. достижение `finish / exit`.

## 8. Камера и читаемость
Камера в прототипе должна помогать платформингу, а не отвлекать.

Каноничное поведение:
- follow camera;
- игрок смещён ближе к нижней центральной зоне кадра;
- используется прямоугольная рамка свободы (`deadzone/frame`);
- внутри неё игрок может двигаться без немедленного движения камеры;
- камера подхватывает игрока, когда он упирается в границу рамки.

## 9. UI-минимум прототипа
В прототипе нужен только минимальный player-facing UI:
- справа внизу: текущая форма и preview форм на `Q/E`;
- сверху: ресурсный UI формы;
- debug UI — нужен.

Ресурсный UI:
- для `Ball` — пустой;
- для `Triangle` — 3 charge icons/segments;
- для `Square` — segmented progress bar trail-resource.

`create/init window` и расширенный UI-фреймворк в scope первого прототипа не входят.

## 10. Death / checkpoint contract
Прототип использует простую модель смерти:
- игрок получает смертельный контакт;
- происходит короткая death pause;
- затем персонаж телепортируется на последний checkpoint.

Checkpoint хранит только позицию.

После смерти:
- форма сбрасывается в `Ball`;
- ресурсы и частные состояния форм сбрасываются;
- оставленные trail/следы игрока очищаются.

## 11. Взаимодействие с миром
Прототип обязан поддерживать:
- статические поверхности;
- наклоны;
- wind zone;
- moving platforms;
- trigger platforms;
- breakable-объекты для Triangle;
- hazard;
- checkpoint;
- finish / exit.

Дополнительно важно, что:
- wind действует на все формы по-разному;
- Square в attach не должен сдуваться;
- moving/trigger platforms должны быть полноценной игровой частью, а не только фоном.

## 12. Технологическая рамка прототипа
Прототип строится как:
- `Phaser-native`;
- `docs-first`;
- `Codex-first`;
- `scene-first / TypeScript-first`.

Правило реализации:
- сначала ищется решение через Phaser scene lifecycle, data/config и узкие runtime-модули;
- затем через `scene/config`, data/config и маленькие runtime-модули;
- только если это начинает ломать механику или слишком усложнять её, допускается небольшой изолированный `TypeScript`.

Прототип не строится вокруг `Box2D / Physics World`. Это управляемый custom platformer.

## 13. Что не входит в scope первого прототипа
Вне scope:
- start window;
- сюжетный слой;
- мета-прогресс;
- сохранения;
- сложный UI-framework;
- расширенная VFX/juice-система;
- большая анимационная система;
- аудио как обязательный системный слой.

Это не запрещено навсегда, но не должно расползать первый канонический прототип.

## 14. Роль этого документа в новой базе
Этот документ должен использоваться как:
- верхнеуровневое описание прототипа;
- входная точка для чтения новой документации;
- опора для feature-docs;
- защита от возврата к старому, смешанному и противоречивому слою описаний.

Этот документ фиксирует обязательные решения по новому прототипу `The Form`.

Если другой новый документ конфликтует с этим файлом, приоритет у этого слоя до явного обновления решения.

Назначение:
- закрепить архитектурные решения;
- зафиксировать input contract;
- зафиксировать form/state behavior rules;
- отделить канон от historical reference.

## 2. Source of truth
При конфликте источников порядок такой:
1. новые решения пользователя, зафиксированные в текущем опросе;
2. этот `prototype_decisions`;
3. `prototype_concept` и новые feature docs;
4. старые MD/DOCX только как historical/reference.

## 3. Архитектурные решения

### 3.1. Общий технологический подход
Принято:
- проект делается как `Phaser-native`;
- подход `docs-first`;
- подход `prefab-by-code-first / TypeScript-first`;
- `TypeScript` разрешён только там, где редакторный / prefab-based подход ломает механику или приводит к неадекватной сложности;
- физическая модель — `custom platformer`, не `Box2D / Physics World`.

### 3.2. Игрок
Принято:
- один `pf_player`;
- внутри него живут три формы: `Ball`, `Triangle`, `Square`;
- это не три независимых player-объекта как основная архитектура;
- все общие системы живут на уровне единого player contract.

### 3.3. Переключение формы
Принято:
- цепочка форм: `Ball -> Triangle -> Square -> Ball`;
- переключение работает в обе стороны через `Q / E`;
- все формы доступны с самого начала test scene;
- стартовая форма — `Ball`;
- форма после смерти — `Ball`;
- переключение в целом разрешено везде;
- у переключения есть короткое состояние трансформации;
- во время трансформации повторное переключение запрещено;
- хитбокс новой формы включается в конце трансформации;
- если новая форма не помещается, переключение отменяется.

## 4. Input contract

### 4.1. Базовые кнопки
- Движение: `WASD`
- `Jump`: `Space`
- `Ability`: `K`
- `Attach` у Square: удержание `K`
- `Regen` у Square: `O`
- `Regen charges` у Triangle: `O`
- Form switch: `Q / E`

### 4.2. Единая ability-кнопка
Принято:
- `Ball` — `K` запускает ускорение;
- `Triangle` — `K` запускает dash;
- `Square` — удержание `K` поддерживает attach.

## 5. Общие системные контракты

### 5.1. Обязательные системные правила
Для всего прототипа обязательны:
- `input buffer`;
- `coyote time`;
- `air control`.

### 5.2. Dynamic jump height
Принято:
- dynamic jump height действует только у обычного jump `Ball` и `Square`;
- у `Triangle` jump отдельный, с собственным контрактом.

### 5.3. Visual marker / точка приложения
Принято:
- это общая игровая системная концепция для `Ball / Triangle / Square`;
- marker всегда видим поверх фигуры;
- marker одинаков по визуальному принципу для всех форм;
- marker влияет на поведение фигур;
- marker двигается плавно, с инерцией и промежуточными положениями даже на клавиатуре;
- при отсутствии ввода marker возвращается в центр;
- у `Triangle` marker связан с ведущим углом и текущей ориентацией.

## 6. Checkpoint / death rules
Принято:
- смерть = короткая death pause -> snap teleport на checkpoint;
- checkpoint сохраняет только позицию;
- после смерти игрок респавнится как `Ball`;
- после смерти всё частное состояние форм сбрасывается;
- после смерти очищаются следы/объекты, оставленные игроком.

После смерти восстанавливается:
- `Triangle charges` -> `3/3`;
- `Square trail resource` -> полный;
- `Ball` не имеет собственного ресурса, но все bounce/boost-состояния сбрасываются.

## 7. Ball — принятые решения

### 7.1. Базовый контракт
- `Ball` — дефолтная форма и форма респавна.
- Коллайдер Ball всегда круглый.

### 7.2. Ускорение
Принято:
- активная способность `K` работает на земле;
- стартует как импульс;
- затем переходит в удерживаемое ускорение;
- если кнопку не удерживать, ускорение короче и слабее;
- у `Ball` нет отдельного ресурса.

### 7.3. Rebound
Принято:
- rebound запускается повторным нажатием `Jump`;
- есть forgiving input / buffer, который прощает раннее нажатие;
- hit pause включается только если rebound реально активирован;
- после запуска rebound идёт по геометрии, input нужен только для самого `Jump`;
- rebound может строиться в бесконечную цепочку, если игрок выдерживает тайминг и геометрию.

### 7.4. Геометрия rebound
Принято:
- wall-bounce имеет upward assist correction;
- floor/ceiling rebound следует правилу отражения по траектории;
- bounce от потолка — полноценная часть механики.

### 7.5. Две высоты прыжка
Принято:
- первый обычный jump с поверхности = высота 1;
- rebound в воздухе = высота 2 и дальнейшее распрыгивание.

## 8. Triangle — принятые решения

### 8.1. Коллизия и ориентация
Принято:
- коллайдер Triangle соответствует форме треугольника;
- ориентация Triangle реально влияет на поведение и коллизию;
- каждая грань может быть опорной;
- Triangle должен в итоге ложиться на грань, а не оставаться на угле или в случайном наклоне.

### 8.2. Jump
Принято:
- jump Triangle не совпадает с обычным jump других форм;
- старт jump происходит через резкий разворот на месте и отталкивание;
- высота и сила jump фиксированы параметрами.

### 8.3. Freeze
Принято:
- повторный `Jump` в воздухе включает freeze;
- повторный `Jump` во freeze не даёт новый freeze, Triangle падает;
- freeze сам по себе заряд не тратит.

### 8.4. Dash
Принято:
- `K` запускает dash;
- dash тратит заряд;
- зарядов: `3`;
- dash возможен:
  - с пола;
  - из воздуха после freeze;
  - из воздуха без freeze;
- dash из воздуха без freeze берёт направление по текущей ориентации Triangle;
- если игрок переключает форму во время dash, форма сохраняет движение по dash-траектории, но новая форма не наследует разрушающие свойства dash.

### 8.5. Реген charges
Принято:
- кнопка `O`;
- доступно только стоя на земле;
- charges возвращаются полностью после короткой задержки и анимации.

### 8.6. Breakable / collision result
Принято:
- только dash Triangle ломает специальные breakable-объекты;
- Ball и Square не ломают их специальным образом;
- breakable-объект исчезает, область становится проходимой, проигрывается простой эффект;
- Triangle может пробить несколько breakable-объектов подряд;
- при ударе в непробиваемую поверхность Triangle застревает углом;
- по `Jump` потом отпрыгивает по нормали поверхности.

### 8.7. Смена формы и состояния Triangle
Принято:
- при смене формы во freeze:
  - freeze снимается;
  - ориентация сбрасывается;
  - charge не тратится;
  - новая форма сразу следует своим правилам.

## 9. Square — принятые решения

### 9.1. Коллизия и поворот
Принято:
- коллайдер Square всегда квадратный;
- реальный поворот Square обязателен;
- реальный поворот важен не только визуально.

### 9.2. Attach
Принято:
- attach возможен к валидной поверхности даже без trail;
- при attach trail начинает строиться;
- если trail уже есть на поверхности, к нему тоже можно attach'иться;
- attach удерживается через `K`.

### 9.3. Attach-compatible surfaces
В первом прототипе attach-compatible:
- пол;
- стены;
- потолок;
- наклоны;
- moving platforms;
- trigger platforms;
- специальные объекты.

### 9.4. Trail-resource
Принято:
- старые `charges` у Square отменены;
- основной ресурс Square = trail-resource;
- ресурс тратится по пройденной дистанции вдоль поверхности;
- если Square стоит, ресурс не тратится;
- если ресурс кончился, Square может стоять, но не может строить новый trail.

### 9.5. Trail persistence / regen
Принято:
- trail глобальный;
- trail живёт, пока не будет собран/восстановлен;
- восстановление идёт от старого к новому;
- auto regen работает только вне attach;
- ручной regen по `O` работает только вне attach;
- если игрок начал новый attach, regen останавливается;
- trail может существовать на движущихся объектах и двигаться вместе с ними.

### 9.6. Attach-jump
Принято:
- attach-jump запускается `Jump`, пока удерживается attach;
- прыжок уменьшенный, фиксированный по высоте, перпендикулярный поверхности;
- визуально связь с trail сохраняется;
- если attach удерживается, Square возвращается назад как натягивание резинки;
- возвращение идёт в актуальное положение attach-zone, а не в старые мировые координаты;
- если attach отпущен, Square отцепляется и переходит в свободное падение.

### 9.7. Rollover
Принято:
- `Square External-Corner Rollover` обязателен в первом прототипе;
- старт rollover автоматический из attach при правильном входе в край;
- attach к потолку — полноценный канон;
- если attach на новой поверхности невозможен, Square возвращается по обратной траектории без смещений.

### 9.8. Смена формы и состояния Square
Принято:
- при смене формы из attach:
  - trail остаётся;
  - attach сразу сбрасывается;
  - квадратные частные состояния обнуляются;
  - новая форма дальше ведёт себя по своим правилам.

## 10. World interaction decisions

### 10.1. Wind
Принято:
- wind влияет на все формы;
- сильнее всего wind влияет на `Ball`;
- затем на `Triangle`;
- слабее всего на `Square`;
- `Square` в attach wind не сдувает;
- wind меняет траекторию прыжка и падения;
- dash Triangle wind замедляет.

### 10.2. Moving / trigger platforms
Принято:
- moving platform и trigger platform входят в обязательный scope test scene;
- они являются полноценной опорной поверхностью;
- Square может attach'иться к ним;
- trail может жить на них и двигаться вместе с ними.

## 11. UI decisions
Принято:
- справа внизу показывается:
  - текущая форма;
  - preview формы на `Q`;
  - preview формы на `E`;
- верхний UI:
  - `Ball` — пустой;
  - `Triangle` — 3 отдельных сегмента/иконки;
  - `Square` — segmented progress bar.
- debug UI входит в scope.
- start window в scope первого прототипа не входит.

## 12. Parameterization decisions
Принято:
- все силы, скорости, тайминги, расстояния, коэффициенты и веса считаются параметрами;
- параметры должны быть описаны в геймдизайнерских единицах, а не в абстрактных внутренних числах;
- базовые типы параметров:
  - секунды;
  - расстояние;
  - скорость;
  - вес;
  - число зарядов/сегментов.

# The Form — Prototype Phaser-Native Implementation Principles

Статус: canonical draft  
Дата: 2026-03-25

## 1. Назначение документа
Этот документ фиксирует правила реализации нового прототипа `The Form` в `Phaser`.

Он нужен, чтобы:
- не скатиться обратно в giant-script архитектуру;
- сохранять `Phaser-native` подход;
- строить прототип через `Scenes`, `TypeScript`, typed config, data-driven wiring и маленькие узкие runtime-модули;
- не подменять архитектуру ручным хаосом и импровизацией “в одном файле”;
- использовать `Codex` как основного исполнителя кода по коротким feature-slice prompt;
- держать `1 prompt -> 1 feature` как целевую рабочую модель там, где это реально без потери точности поведения.

Этот документ задаёт именно **принципы реализации**, а не описывает механику саму по себе.

---

## 2. Базовый implementation stance
Для прототипа принят такой порядок приоритетов:

1. **Docs-first**
2. **Codex-first**
3. **Scene-first**
4. **TypeScript-first для core gameplay logic**
5. **Small-module-first**
6. **Data/config-first**
7. **Visual tooling only if it is clearly local and not core**

Это означает:

- сначала читаем канон и только релевантные `feature_*` документы;
- затем определяем минимальный slice, который должен быть реализован за текущий проход;
- затем собираем короткий prompt для `Codex`;
- core-feel логику не распыляем по giant controller-файлам;
- если что-то можно держать как ясную scene/config/data настройку — держим так;
- если поведение, геометрия или state machine требуют кода — пишем узкий изолированный `TypeScript`;
- визуальные редакторы, внешние graph-слои и heavy plugin-driven workflow не должны становиться источником истины.

---

## 3. Что считается Phaser-native подходом

### 3.1. Приоритет ресурсов движка и проекта
Решения по возможности должны опираться на:

- `Phaser Scenes`;
- scene lifecycle (`init / preload / create / update`);
- `GameObjects`, `Containers`, `Groups`, `Cameras`, `Tweens`, `Timers`;
- typed config objects;
- маленькие runtime-классы и helper-модули;
- чётко разделённые gameplay / ui / debug / world / data слои;
- asset-loader слой;
- scene-local wiring;
- data assets (`json`, `tilemap properties`, config modules), если они реально упрощают tuning.

### 3.2. Что не считается желательным подходом
Нежелательно:

- выносить почти всю игру в один гигантский `update`;
- делать один гигантский `player.ts`, который знает всё о мире, UI, debug и каждой форме сразу;
- строить архитектуру «как будто это не Phaser, а абстрактный движок без lifecycle и scene model»;
- прятать ключевую механику за большим количеством неочевидных helper-слоёв;
- тащить в проект сложный внешний editor-only workflow ради того, что в Phaser проще и чище описывается кодом и config;
- превращать Codex в “переписчик всего проекта за один запрос”.

---

## 4. Главный объект игрока

### 4.1. Канон
Принято:

- один `pf_player`;
- три формы внутри одного player contract: `Ball`, `Triangle`, `Square`;
- общие системы живут в этом же общем слое;
- форма — это режим/состояние игрока, а не отдельная архитектурная ветка с дублированием всего core.

### 4.2. Что означает `pf_*` в Phaser-версии
В этой документации префикс `pf_*` сохраняется как **логический идентификатор повторно используемой сущности**, но в Phaser это не Unity Prefab-asset.

Под `pf_*` здесь понимается один из вариантов:

- factory-функция;
- класс-обёртка над `Container`/`GameObject`;
- prefab-by-code builder;
- scene recipe с понятным публичным API.

То есть имя остаётся, а техническая реализация переезжает в Phaser-эквивалент.

### 4.3. Что выносится в отдельные объекты
Отдельные сущности допустимы и желательны для:

- checkpoint;
- hazards;
- breakable;
- moving platforms;
- trigger platforms;
- wind zones;
- trail representation, если это удобнее как world-state слой;
- UI helper objects;
- debug helpers.

---

## 5. Правило по scene/config wiring

### 5.1. Где использовать по максимуму
Scene/config/data wiring приоритетно использовать для:

- boot flow;
- scene setup;
- reference linking;
- world composition;
- checkpoint activation;
- trigger-логики;
- простых UI-реакций;
- platform path setup;
- camera target assignment;
- debug visibility toggles;
- placeholder asset wiring;
- tuning параметров.

### 5.2. Где этого, скорее всего, не хватит
Ожидаемо сложными зонами являются:

- real orientation логика `Triangle`;
- `Ball` bounce / rebound / chain logic;
- `Square` attach / trail / rollover;
- нестандартная геометрия и rotated contacts;
- точный player state contract;
- form switching внутри активных под-состояний.

Для этих зон канонически допускается узкий `TypeScript`.

---

## 6. Правило по TypeScript

### 6.1. Когда TypeScript обязателен
`TypeScript` обязателен там, где без кода невозможно сохранить:

- точную механику;
- предсказуемую геометрию;
- контролируемую state machine;
- читаемый runtime contract;
- ясные acceptance-критерии.

### 6.2. Какой TypeScript считается правильным
Правильный `TypeScript` здесь — это:

- маленькие файлы;
- узкие зоны ответственности;
- явные входы/выходы;
- минимум скрытой магии;
- без giant switchboard-файлов;
- без “один бог-контроллер управляет всем”.

### 6.3. Что считается плохим TypeScript
Плохим считается:

- гигантский файл на сотни строк без ясных границ;
- смешение gameplay + ui + debug + asset loading + scene bootstrap;
- код, который нельзя изолированно отдать Codex как короткий feature-slice;
- код, который невозможно проверить по acceptance без чтения половины проекта.

---

## 7. Структура player-логики
Даже при одном `pf_player` логика игрока должна быть разделена хотя бы концептуально на:

- player core state;
- current form state;
- input interpretation;
- marker logic;
- movement / collision logic;
- per-form abilities;
- camera-facing data;
- UI-facing data;
- debug-facing data.

Это не означает, что на старте нужно создать десятки файлов “про запас”.
Это означает, что **при добавлении новой ответственности** она не должна бесконтрольно липнуть к уже существующему файлу.

---

## 8. Геометрия и коллизии
Прототип не строится как physics-sim first.
Канон остаётся таким же, как и в исходных документах:

- platformer-feel первичен;
- точный игровой контракт первичен;
- full rigid-body simulation не является целью первого прототипа;
- поведение должно быть контролируемым, а не “как получилось у physics engine”.

В Phaser это означает:

- физика движка используется как инструмент, а не как источник канона;
- если стандартный physics-body даёт нужный результат — допустимо использовать;
- если стандартный body ломает нужный контракт, геометрия реализуется собственным gameplay-слоем поверх или вместо engine-default поведения;
- сложные углы, attach, rollover и orientation-сценарии нельзя “сдать на волю движка”, если это ломает механику.

---

## 9. Test scene как основной truth environment
`sc_test` — это основная каноническая среда проверки.

Она нужна не для красоты, а для:

- проверки всех форм;
- form switching;
- hazards / checkpoint / wind / moving platform / trigger platform / breakables;
- camera behavior;
- square attach / trail / rollover;
- fast regression-проверки после каждого feature-slice.

Любой slice, который не проверяется в `sc_test`, считается незавершённым или хотя бы недопроверенным.

---

## 10. UI и debug
UI и debug не должны быть слиты с player-core.

Допустимо:

- держать UI как отдельный scene-layer;
- держать debug helpers как отдельный слой;
- пробрасывать наружу только нужные данные;
- иметь временный placeholder UI.

Недопустимо:

- чтобы player-core напрямую рендерил весь UI мира;
- чтобы debug-only логика диктовала структуру gameplay;
- чтобы feature-slice считался готовым без хотя бы минимального debug/acceptance способа увидеть результат.

---

## 11. Параметризация как часть реализации
Параметры — это часть архитектуры, а не косметика после кода.

Новый tuning-параметр должен:

- иметь понятное имя;
- иметь понятную единицу смысла;
- жить в предсказуемом config-слое;
- не требовать поиска по десятку файлов;
- быть достаточно локальным, чтобы Codex мог менять его без чтения всего проекта.

Для Phaser-версии допустимо хранить параметры:

- в typed config modules;
- в `json` tuning-файлах;
- в scene-local config;
- в data properties tilemap/object слоя, если это действительно уместно.

---

## 12. Правило по visual tooling
В этой версии прототипа visual tooling не является основой реализации.

Допустимо:

- использовать тайлмап-редактор, object layers, asset-pipeline utilities;
- использовать внешние инструменты только как support-слой.

Недопустимо:

- делать core-mechanics зависимыми от тяжёлого визуального graph workflow;
- строить систему так, чтобы без конкретного editor-инструмента её было невозможно понять;
- раздувать scope ради псевдо-редакторного подхода, которого Phaser от природы не требует.

---

## 13. Правило по Codex prompt workflow

### 13.1. Какой slice считается правильным
Правильный slice для Codex — это тот, у которого есть:

- одна узкая цель;
- фиксированный scope;
- список релевантных документов;
- список файлов, которые можно трогать;
- acceptance-критерии;
- запрет на побочные архитектурные переделки.

### 13.2. Что должно попасть в prompt
В prompt для Codex должны попадать только:

- задача текущего slice;
- нужные doc paths;
- канонические ограничения;
- файлы, которые разрешено менять;
- файлы, которые трогать нельзя;
- ожидаемый результат;
- ожидаемый формат ответа.

Не нужно вставлять в prompt весь проект и все документы, если для текущей фичи это не требуется.

### 13.3. Что считается хорошим результатом
Хороший результат для этого проекта — когда:

- feature реализована в одном проходе;
- логика локальна;
- файлы не раздулись;
- новый код не ломает канон;
- acceptance можно проверить сразу в `sc_test`.

---

## 14. Правило по именованию и читаемости
Имена должны быть:

- стабильными;
- короткими, но не загадочными;
- одинаково читаемыми человеком и Codex;
- единообразными по стилю.

Рекомендуемо:

- `snake_case` для asset ids и doc ids;
- понятные scene keys;
- одинаковые префиксы для world/player/ui/debug сущностей;
- file name ≈ ответственность файла.

---

## 15. Итоговый implementation contract
Новый Phaser-прототип `The Form` собирается так:

- механический канон сохраняется;
- `Scenes`, scene lifecycle, asset/data/config и узкие `TypeScript` модули используются максимально;
- `Codex` работает короткими slice-задачами;
- стремимся к модели `1 prompt -> 1 готовая feature`, но не ценой архитектурной грязи;
- giant-file и giant-controller подход запрещён;
- `sc_test` остаётся главной средой проверки;
- любая новая реализация должна быть достаточно локальной, чтобы её можно было безопасно дать Codex без гигантского контекста.

# The Form — Codex Feature Prompt Contract (RU, Phaser)

Статус: working canonical support doc  
Дата: 2026-03-25

## 1. Назначение документа
Этот документ фиксирует, **как именно нужно готовить prompt для Codex** при разработке `The Form` на `Phaser`.

Его задача:

- сохранить короткий и релевантный контекст;
- уменьшить расход токенов Codex;
- повысить шанс на модель `1 prompt -> 1 готовая feature slice`;
- не давать Codex расползаться в лишние переделки;
- поддерживать маленькие, атомарные, проверяемые изменения.

---

## 2. Главный принцип
Codex не должен получать весь проект “на всякий случай”.

Codex должен получать только:

- цель текущего slice;
- минимальный набор документов;
- минимальный набор файлов;
- явные ограничения;
- acceptance.

Чем уже и точнее prompt, тем выше шанс на правильный результат и тем ниже расход токенов.

---

## 3. Что должно быть в каждом prompt

### 3.1. Обязательные блоки
Каждый prompt для Codex должен содержать:

1. **Тип задачи**
2. **Цель slice**
3. **Какие документы читать**
4. **Какие файлы проекта читать**
5. **Какие файлы можно менять**
6. **Какие файлы менять нельзя**
7. **Ограничения по архитектуре**
8. **Acceptance criteria**
9. **Формат ответа Codex**

---

## 4. Рекомендуемый компактный шаблон prompt

```text
Работаем по проекту The Form (Phaser / TypeScript).

Тип задачи:
PHASER_ONLY / DOC_ONLY / MIXED_PHASER_DOC / ANALYSIS_ONLY

Цель:

Сначала прочитай документы:
- <doc 1>
- <doc 2>
- <doc 3>

Затем прочитай только эти файлы проекта:
- <file 1>
- <file 2>
- <file 3>

Разрешено менять только:
- <file A>
- <file B>

Нельзя менять:
- <file X>
- <file Y>

Архитектурные ограничения:
- Phaser-native
- docs-first / Codex-first
- small-module-first
- не раздувать giant files
- не делать побочных рефакторингов вне slice
- не ломать существующий канон форм и test scene

Что нужно сделать:
- <конкретный список действий>

Acceptance:
- <проверка 1>
- <проверка 2>
- <проверка 3>

Формат ответа:
1. Что прочитал
2. Что изменил
3. Почему это соответствует канону
4. Какие риски / open questions остались
```

---

## 5. Как выбирать документы
В prompt должны попадать только релевантные документы.

### Примеры
#### Для Ball feature
Достаточно:
- `the_form_prototype_decisions_ru.md`
- `the_form_feature_ball_ru.md`
- `the_form_prototype_parameters_registry_ru.md`

#### Для camera feature
Достаточно:
- `the_form_prototype_decisions_ru.md`
- `the_form_feature_camera_ru.md`
- `the_form_test_scene_spec_ru.md`

#### Для form switching
Достаточно:
- `the_form_prototype_decisions_ru.md`
- `the_form_feature_form_switching_ru.md`
- при необходимости `the_form_feature_input_and_marker_ru.md`

Не нужно добавлять все `feature_*` документы сразу, если они не нужны текущему slice.

---

## 6. Как выбирать файлы проекта
В prompt должны попадать только те файлы, без которых нельзя реализовать slice.

### Правило
Если фича может быть реализована через 2–6 файлов, не надо давать 15.

### Хорошо
- текущая сцена;
- текущий player module;
- один helper;
- один config файл;
- один UI/debug файл при необходимости.

### Плохо
- весь `src/game`;
- весь `src`;
- все сцены;
- все формы сразу, если задача только про `Ball`.

---

## 7. Когда slice слишком большой
Slice считается слишком большим для одного prompt, если:

- в него входят несколько механик сразу;
- он требует чтения половины документов;
- он требует изменения большого числа unrelated файлов;
- acceptance нельзя проверить одной короткой серией тестов.

Тогда slice надо делить.

---

## 8. Что Codex не должен делать
Codex не должен:

- самовольно менять архитектуру за пределами scope;
- переименовывать полпроекта;
- трогать unrelated формы;
- внедрять новую framework-надстройку без явного запроса;
- переписывать существующий working slice “потому что так красивее”.

---

## 9. Что считается хорошим ответом Codex
Хороший ответ Codex:

- сначала перечисляет, что прочитал;
- явно указывает изменённые файлы;
- делает только нужный slice;
- не создаёт giant files;
- уважает канон;
- честно перечисляет риски и open questions.

---

## 10. Практическое правило минимизации токенов
Чтобы уменьшать расход токенов Codex:

- не вставлять длинные цитаты из документов, если можно сослаться на путь и нужный раздел;
- не перечислять нерелевантные файлы;
- не просить сразу “сделай всё полностью”;
- не давать несколько конкурирующих задач в одном prompt;
- держать acceptance коротким и проверяемым.

---

## 11. Итоговый workflow
Правильный pipeline выглядит так:

1. Пользователь формулирует задачу.
2. Я определяю релевантные документы и релевантные файлы.
3. Я собираю короткий prompt.
4. Codex делает один feature-slice.
5. Slice проверяется в `sc_test`.
6. После этого начинается следующий slice.

Это и есть каноническая рабочая модель Phaser-версии документации `The Form`.

# The Form — Prototype Parameters Registry

Статус: canonical draft  
Дата: 2026-03-25

## 1. Назначение документа
Этот документ фиксирует реестр параметров нового прототипа `The Form`.

Его задача:
- перечислить параметры, которые должны быть доступны для настройки;
- задать понятные, геймдизайнерские единицы измерения;
- отделить `design-facing parameters` от скрытых технических величин;
- не допустить возврата к hardcoded-настройкам.

Если в будущем конкретные стартовые значения изменятся, это не меняет структуру реестра: сам реестр является каноничным, а числа могут тюниться.

---

## 2. Общие правила параметризации

### 2.1. Что считается обязательным правилом
Все ключевые тайминги, силы, расстояния и лимиты прототипа должны задаваться параметрами.

### 2.2. Как параметры должны выглядеть
Параметры должны быть описаны в понятных единицах:
- время — в секундах;
- расстояние — в пикселях или тайлах;
- скорость — в пикселях в секунду;
- ускорение/замедление — в пикселях в секунду в секунду;
- углы — в градусах;
- заряд/ресурс — в сегментах, процентах или длине следа;
- вес формы — в явной игровой величине, а не в абстрактном коэффициенте без смысла.

### 2.3. Что запрещено
Не считаются хорошим каноном:
- скрытые магические числа;
- параметры без единиц измерения;
- параметры, смысл которых нельзя объяснить дизайнеру;
- дублирующие параметры, описывающие одно и то же разными именами.

### 2.4. Слои параметров
Параметры делятся на два слоя:

1. **Design-facing** — те, что можно объяснить через ощущение игры.
2. **Technical-supporting** — те, что нужны для реализации, но не должны подменять игровые решения.

Для первого прототипа приоритет у design-facing слоя.

---

## 3. Глобальные параметры прототипа

### 3.1. Общие системные тайминги
Обязательные параметры:
- `jump_buffer_time_sec` — окно buffer input для прыжка;
- `attach_buffer_time_sec` — окно buffer input для attach Square;
- `coyote_time_sec` — время кайота для форм, где есть обычный jump;
- `death_pause_time_sec` — длительность паузы перед респавном;
- `form_transform_time_sec` — длительность трансформации между формами;
- `wind_update_blend_time_sec` — насколько быстро форма ощущает изменение ветра, если нужен сглаженный отклик.

### 3.2. Общие параметры движения
- `ground_move_speed_px_per_sec` — базовая скорость по земле;
- `ground_accel_px_per_sec2` — ускорение по земле;
- `ground_decel_px_per_sec2` — торможение по земле;
- `air_control_speed_px_per_sec` — максимальная управляемая добавка в воздухе;
- `air_control_accel_px_per_sec2` — скорость набора управления в воздухе;
- `gravity_px_per_sec2` — базовая гравитация;
- `fall_speed_cap_px_per_sec` — предел скорости падения.

### 3.3. Marker / точка приложения
- `marker_move_speed_px_per_sec` — скорость движения marker внутри фигуры;
- `marker_return_speed_px_per_sec` — скорость возврата marker к центру без ввода;
- `marker_max_offset_px` — максимальное смещение marker от центра фигуры;
- `marker_smoothing_time_sec` — инерционность marker;
- `marker_visual_scale` — визуальный размер marker.

### 3.4. Вес форм
Так как вес фигур является частью игрового канона, он должен существовать как явный набор параметров:
- `ball_weight_value`
- `triangle_weight_value`
- `square_weight_value`

Эти параметры затем используются в системах вроде wind и, при необходимости, в других взаимодействиях.

## 4. Параметры Ball

### 4.1. Обычное движение Ball
- `ball_ground_speed_px_per_sec`
- `ball_ground_accel_px_per_sec2`
- `ball_ground_decel_px_per_sec2`
- `ball_air_control_speed_px_per_sec`
- `ball_air_control_accel_px_per_sec2`
- `ball_normal_jump_height_px` — первая высота прыжка;
- `ball_jump_hold_time_sec` — сколько удержание влияет на высоту обычного jump;
- `ball_jump_release_gravity_multiplier` — насколько сильнее форма начинает терять подъём после отпускания прыжка.

### 4.2. Ускорение Ball
- `ball_boost_start_impulse_px_per_sec` — стартовый импульс при активации `K`;
- `ball_boost_hold_speed_px_per_sec` — скорость при удерживаемом ускорении;
- `ball_boost_accel_px_per_sec2` — скорость добора до удерживаемого ускорения;
- `ball_boost_decel_px_per_sec2` — скорость замедления после завершения ускорения;
- `ball_boost_min_ground_contact_time_sec` — если понадобится минимальный надёжный контакт с землёй;
- `ball_boost_turn_resistance` — насколько тяжело менять направление в активном ускорении.

### 4.3. Rebound Ball
- `ball_rebound_input_window_sec` — окно, в которое прощается ранний повторный `Jump`;
- `ball_rebound_hit_pause_sec` — длительность hit pause при успешном rebound;
- `ball_rebound_level1_height_px` — первая высота прыжка с поверхности;
- `ball_rebound_level2_height_px` — усиленная высота rebound-chain;
- `ball_rebound_wall_assist_upward_px_per_sec` — вертикальная коррекция rebound от стены;
- `ball_rebound_floor_reflect_ratio`
- `ball_rebound_ceiling_reflect_ratio`
- `ball_rebound_wall_reflect_ratio`

Если позже потребуется ограничить runaway-сценарии, это делается через отдельный канонический параметр, а не через скрытые clamp-и.

## 5. Параметры Triangle

### 5.1. Обычное перемещение Triangle
- `triangle_ground_speed_px_per_sec`
- `triangle_ground_accel_px_per_sec2`
- `triangle_ground_decel_px_per_sec2`
- `triangle_air_control_speed_px_per_sec`
- `triangle_air_control_accel_px_per_sec2`
- `triangle_gravity_px_per_sec2`

### 5.2. Специальный jump Triangle
Triangle не использует обычный jump как Ball и Square.

Обязательные параметры:
- `triangle_jump_turn_time_sec` — длительность начального разворота перед отталкиванием;

# The Form — Phaser Project Structure (RU)

## Назначение документа

Этот документ фиксирует **целевую структуру нового проекта The Form** для прототипа, который собирается в подходе:

- `Phaser-native`
- `docs-first`
- `Codex-first`
- `scene-first`
- `TypeScript-first`
- `small-module-first`
- `minimal external tooling only when clearly better`

Документ отвечает на вопросы:

- какие папки и слои должны быть в проекте;
- какие сцены нужны на старте;
- что должно быть отдельным модулем, а что — частью `pf_player`;
- где допустим config/data wiring, а где почти наверняка нужен узкий `TypeScript`;
- как избежать возврата к giant central script / god-object архитектуре.

---

## Главные структурные принципы

### 1. Один `pf_player`, три формы внутри него
Игрок реализуется как **один основной prefab-by-code module**:

- `pf_player`

Внутри него живут:

- общие системы игрока;
- текущая форма;
- form switching;
- input buffer / coyote time / death / checkpoint reset;
- marker;
- общие state-переменные;
- делегирование поведения форме.

Не создаём три отдельных player-пути как основную архитектуру.

---

### 2. Вспомогательные системы — отдельными scene object / factory / module слоями
Отдельными сущностями должны быть:

- checkpoint;
- hazards;
- breakable-объекты;
- moving platform;
- trigger platform;
- wind zone;
- UI;
- scene bootstrap;
- camera controller;
- trail-support объекты, если без них удобнее, чем держать всё внутри `pf_player`.

---

### 3. Не делать giant central controller
Нельзя сваливать всю игру в:

- один гигантский `update`;
- один гигантский `player` файл;
- один центральный controller, который знает всё о мире, UI, debug и каждой форме сразу.

Даже если часть логики живёт внутри `pf_player`, она должна быть **разделена по понятным runtime-модулям, typed config группам и узким зонам ответственности**.

---

### 4. Папки должны отражать смысл, а не только тип ресурса
Структура должна помогать ориентироваться в проекте:

- `assets`
- `src/scenes`
- `src/game/player`
- `src/game/world`
- `src/game/camera`
- `src/ui`
- `src/debug`
- `src/config`
- `docs`

а не просто “все файлы в одной куче”.

---

### 5. Временные placeholder-ассеты допустимы
На этапе прототипа допустимо использовать:

- простые геометрические спрайты;
- цветовые заглушки;
- технические placeholder-иконки;
- временные json/tilemap layouts.

Но структура должна быть такой, чтобы потом ассеты можно было заменить без переделки логики.

## Сцены

### 1. `sc_bootstrap`
Назначение:

- стартовая техническая сцена;
- preload базовых ассетов и конфигурации;
- запуск `sc_test`;
- very-thin bootstrap слой, а не игровой уровень.

На самом первом прототипе может быть очень простой.

Возможный состав:

- загрузка assets;
- регистрация данных;
- запуск `sc_test`.

Если отдельный boot-flow не нужен, допустимо минимизировать этот слой, но **каноничнее иметь `sc_bootstrap`**.

---

### 2. `sc_test`
Главная каноническая test scene.

Назначение:

- проверка всех форм;
- проверка form switching;
- проверка hazards / checkpoint / wind / platforms / breakables;
- проверка camera;
- проверка Square attach / trail / rollover.

Именно эта сцена является основным полигоном прототипа.

Подробный состав — в `the_form_test_scene_spec_ru.md`.

## Prefab-by-code modules: core

### `pf_bootstrap`
Роль:

- стартовая инициализация прототипа;
- загрузка базовых данных;
- переход в `sc_test`;
- тонкий boot слой, не второй game framework.

В идеале:

- маленький boot runner;
- минимум логики;
- без превращения bootstrap в центральный god-object.

---

### `pf_game_controller` (опционально)
Нужен только если станет очевидно, что:

- bootstrap-слою тесно;
- глобальные правила прототипа требуют отдельного контроллера;
- появились системы, которые неестественно держать либо в `pf_bootstrap`, либо в `pf_player`.

На старте **не обязателен**. Не создавать “на всякий случай”.

---

### `pf_camera_controller`
Отдельный слой камеры / rig.

Почему отдельно:

- камера — системный слой;
- её лучше не смешивать с `pf_player`;
- так проще настраивать deadzone / bias / smoothing.

Содержит:

- target reference;
- frame / deadzone;
- follow rules;
- smoothing rules.

Для базовой камеры достаточно:

- `Camera`;
- player target;
- typed tuning fields;
- узкий follow-модуль.

Если логика deadzone начнёт требовать неудобной математики — допустим узкий `TypeScript`.

---

## Prefab-by-code modules: player

### `pf_player`
Главный player module.

#### Внутри него должны жить группы логики
- common input
- common timers
- form switching
- base movement shell
- marker
- death / checkpoint reset
- shared state
- per-form delegation

#### Что не должно происходить
Нельзя, чтобы `pf_player` сразу превратился в один giant file.
Даже при одном основном player-модуле внутренняя логика должна быть разбита на понятные части.

---

### Отдельные player-support слои (по необходимости)
Допустимы:

- `pf_player_marker`
- `pf_player_trail_renderer`
- `pf_player_form_visuals`
- `pf_player_debug_overlay`

На старте предпочтительно сначала попробовать без лишнего дробления, но **дробить допустимо**, если это уменьшает сложность core-файла и делает slice проще для Codex.

## Prefab-by-code modules: world

### Базовые world-сущности
Должны иметь отдельные модули/фабрики:

- `pf_solid_block`
- `pf_slope_block`
- `pf_breakable_block`
- `pf_checkpoint`
- `pf_hazard`
- `pf_moving_platform`
- `pf_trigger_platform`
- `pf_wind_zone`

Это не обязательно должны быть отдельные классы на каждый пиксельный блок.
Это означает, что **каждый тип world-behavior должен иметь ясную точку сборки**.

### Что допустимо
Если в Phaser удобнее держать часть уровня как tilemap/object layer, а часть как runtime-created objects — допустимо.
Главное, чтобы поведенческие роли были разделены и читались.

## TypeScript / minimal runtime modules

### Базовое правило
Код делим по смыслу, а не по случайности.

Предпочтительные группы:

- `src/game/player`
- `src/game/forms`
- `src/game/world`
- `src/game/camera`
- `src/ui`
- `src/debug`
- `src/config`
- `src/shared`

### Чего избегаем
Избегаем:

- giant central files;
- смешения разных ответственностей;
- файлов, которые невозможно безопасно менять коротким prompt для Codex;
- скрытого coupling между unrelated системами.

Не нужно заранее создавать:

- тяжёлую data-driven framework оболочку;
- редакторские утилиты, которые пока не обслуживают конкретный slice;
- сетевую архитектуру;
- красивый production UI.

## Практическое правило по сборке через Codex
Структура проекта должна быть такой, чтобы типовой prompt для Codex мог ссылаться на:

- 2–5 релевантных документов;
- 1–6 файлов проекта;
- один чёткий acceptance outcome.

Если для одной фичи нужно читать 20 файлов и полпроекта, структура уже стала слишком сцепленной.

## Итоговый structural contract
Новый Phaser-проект `The Form` должен быть устроен так, чтобы:

- механический канон сохранялся;
- сцены, assets, config и code modules были разделены;
- player-core не превращался в giant-file;
- world/UI/debug не липли к одной сущности;
- любая feature могла реализовываться коротким Codex prompt;
- `sc_test` оставалась главной средой проверки;

# The Form — зафиксированные принятые решения по новому прототипу

## Статус документа
Этот документ фиксирует решения, принятые пользователем в ходе уточняющего опроса по новому прототипу `The Form`.

Назначение документа:
- зацементировать итоговое видение прототипа;
- защитить новые решения от потери при переписывании старых MD/DOCX;
- служить отдельным reference-слоем при сборке новой каноничной MD-документации.

## Приоритет источников истины
При противоречиях между старыми документами и этим слоем приоритет такой:
1. новые зафиксированные решения пользователя;
2. новая MD-документация, собранная на их основе;
3. старые MD/DOCX — только как historical reference.

## Цель первого прототипа
Приоритет целей:
1. `B` — собрать вертикальный срез с ощущением настоящей игры;
2. `A` — проверить, что ядро механик ощущается правильно;
3. `C` — технически проверить контракт форм.

## Общий подход к разработке
- Подход: `Phaser-native`, `docs-first`, `prefab-by-code-first`, `TypeScript-first`.
- Реализация по максимуму через Phaser Scenes, typed config/data и структуру проекта, prefab-by-code modules, runtime modules, typed config fields и scene/config.
- TypeScript допускается только там, где редакторное / prefab-based решение даст хрупкий, ложный или слишком неудобный результат.
- Прототип строится как `custom platformer`, не через `Box2D / Physics World`.

## Архитектурный каркас игрока
- Один `pf_player`.
- Внутри одного объекта живут три формы: `Ball`, `Triangle`, `Square`.
- Переключение формы цикличное:
  - `Ball → Triangle → Square → Ball`;
  - работает в обе стороны через `Q / E`.
- Все три формы доступны с самого начала `test scene`.
- Смена формы работает везде, но имеет короткое состояние трансформации с блокировкой повторного переключения.
- Новый хитбокс формы включается в конце трансформации.
- Если новая форма не помещается в текущем месте, переключение отменяется.
- Стартовая форма и форма после смерти: `Ball`.

## Контракт управления
- Движение: `WASD`.
- `Jump`: `Space`.
- `Ability`: `K`.
- `Attach` для Square: удержание `K`.
- `Regen`:
  - `O` — восстановление trail у Square;
  - `O` — восстановление зарядов у Triangle.
- `Q / E` — смена формы.

## Общие системные правила для всех форм
Обязательны для всего прототипа:
- `input buffer` для прыжка;
- `coyote time` для прыжка;
- управление в воздухе (`air control`);
- общая видимая `точка приложения силы / энергии` как системная концепция для всех форм.

### Точка приложения силы / энергии
- Это общая игровая системная концепция для `Ball / Triangle / Square`.
- Игрок должен видеть её всегда.
- Marker всегда видим поверх фигуры.
- Marker одинаковый по визуальному языку для всех форм.
- Marker влияет на поведение фигур.
- В первом прототипе marker уже является видимым элементом игры, а не только debug-слоем.
- Marker двигается внутри фигуры плавно, с промежуточным положением и инерцией даже на клавиатуре.
- При отсутствии ввода marker возвращается в центр.
- У Triangle есть ведущий угол, связанный с текущей ориентацией и visual marker.

### Прыжок и движение
- `dynamic jump height` применяется только к обычному jump у `Ball` и `Square`.
- Для этих прыжков все величины описываются в вещественных, геймдизайнерских параметрах: время в секундах, расстояния, скорости, силы и т. д.
- Вес фигур также считается параметром, настраиваемым с геймдизайнерской точки зрения.

## Смерть и checkpoint
- Урон/смерть в прототипе: короткая пауза смерти, затем `snap teleport` на последний checkpoint.
- Checkpoint сохраняет только позицию.
- После смерти игрок всегда респавнится как `Ball`.
- После смерти всё состояние полностью сбрасывается:
  - заряды Triangle;
  - trail и trail-resource Square;
  - rebound/boost-состояния Ball;
  - текущие частные состояния форм;
  - оставленные игроком следы и связанные с ними специфические объекты/состояния.

## Камера
- Камера следует за игроком.
- Игрок должен находиться ближе к нижней центральной зоне кадра.
- Камера имеет прямоугольную `рамку свободы` (`deadzone/frame`):
  - пока игрок движется внутри неё, камера не реагирует;
  - когда игрок упирается в её край, камера догоняет.
- Главная цель камеры — читаемость платформинга, а не кинематографичность.

## Обязательный состав test scene
В первой `test scene` должны быть:
- ровный пол;
- стены;
- потолок;
- наклоны;
- узкий колодец между двумя стенами для Ball;
- внешний угол для Square rollover;
- hazard;
- checkpoint;
- breakable wall для Triangle;
- moving platform;
- trigger platform;
- wind zone.

## Обязательные объекты и системы уровня
В минимуме прототипа должны поддерживаться:
- пол, стены, потолок, наклонные поверхности;
- hazard;
- checkpoint;
- finish / exit;
- wind zone;
- moving platforms;
- trigger platforms.

## Form Switching — канон поведения
- Переключение форм работает в любом состоянии, если не заблокировано текущим состоянием трансформации.
- Во время трансформации повторное переключение запрещено.
- По умолчанию при смене формы сохраняются:
  - скорость;
  - направление движения;
  - положение visual marker.
- Но `state-specific` исключения сильнее общих правил:
  - при выходе из `Square attach` attach-state сбрасывается;
  - при выходе из `Triangle freeze` ориентация сбрасывается;
  - при выходе из `Triangle dash` сохраняется движение по dash-вектору, но новая форма уже не наследует специальные свойства dash.

## Ball — канон
### Базовая роль формы
Ball — дефолтная форма и форма респавна.

### Способность
- Активная способность (`K`) — ускорение.
- Ускорение работает на земле.
- Стартует как импульс.
- После импульса идёт замедление и удерживаемое ускорение:
  - если кнопку не удерживать, поведение короче и слабее;
  - если удерживать, Ball движется быстрее, чем без способности.
- У Ball нет собственного ресурса.

### Rebound / bounce
- Для rebound игрок должен повторно нажать `Jump`.
- Действует forgiving input / jump buffer: если игрок нажал чуть раньше, rebound всё равно должен сработать.
- `hit pause` включается только если rebound реально активирован.
- Во время rebound `input` нужен только для самого `Jump`; дальше rebound идёт автоматически по геометрии.
- Цепочка rebound может быть бесконечной, если игрок точно попадает по таймингу и геометрии.

### Геометрия rebound
- От стен rebound идёт с лёгкой коррекцией траектории вверх, чтобы можно было прыгать между узко поставленными стенами.
- При вертикальном rebound от пола и потолка действует правило: угол падения равен углу отражения.
- Bounce от потолка — полноценный rebound-механизм, а не просто гашение скорости вниз.

### Две высоты прыжка
- Первый обычный прыжок с поверхности — `высота 1`.
- Если Ball уже находится в воздухе и делает rebound от поверхности, это `высота 2`.
- Идея: второй и последующие rebound-прыжки работают как распрыгивание и дают более сильный прыжок, чем первый стартовый.

### Коллайдер
- Коллайдер Ball всегда круглый.

## Triangle — канон
### Базовая роль формы
Triangle — самая сложная и наиболее чувствительная к ориентации форма.

### Коллизия и ориентация
- Коллайдер Triangle должен реально соответствовать форме треугольника.
- Ориентация Triangle реально учитывается.
- Каждая грань Triangle может быть опорной поверхностью для движения.
- После падения/столкновения Triangle должен в итоге лечь полноценно на грань, а не зависнуть на угле или под случайным наклоном.

### Прыжок
- У Triangle нет обычного jump в том же виде, что у Ball и Square.
- Его стартовый прыжок — отдельная специальная механика:
  - Triangle резко разворачивается на месте;
  - получает вращательное движение;
  - отталкивается от поверхности.
- Этот jump работает по общим принципам прыжка, но начинается через поворот.
- Высота и сила такого прыжка — фиксированные параметры.

### Freeze
- В воздухе повторное нажатие `Jump` включает `freeze`.
- Если во `freeze` снова нажать `Jump`, ничего не происходит, Triangle падает вниз.
- Freeze сам по себе заряд не тратит.

### Dash
- `Ability` (`K`) запускает `dash`.
- Dash можно сделать:
  - с пола, если один из углов расположен перпендикулярно опорной поверхности;
  - из воздуха после freeze;
  - из воздуха без freeze.
- Если dash делается из воздуха без freeze, направление dash берётся по текущей ориентации Triangle.
- Dash тратит заряд.
- У Triangle `3` заряда dash.
- Заряды показываются в UI.

### Реген зарядов
- Кнопка `O`.
- Восстановление доступно стоя на земле.
- Восстановление происходит не мгновенно по нажатию, а мгновенно после короткой задержки и анимации.
- После завершения регена заряды возвращаются полностью (`3/3`).

### Breakable-объекты
- Только dash Triangle ломает специальные breakable-объекты.
- Ball и Square не имеют специального разрушающего взаимодействия с ними.
- После поломки объект исчезает, зона становится проходимой для других форм, проигрывается простой эффект/анимация.
- Triangle может пробить несколько breakable-объектов подряд и продолжить dash.

### Удар в непробиваемую поверхность
- Если Triangle во время dash бьётся в непробиваемую поверхность, он застревает в ней углом.
- По нажатию `Jump` он отпрыгивает по нормали поверхности.
- После этого входит в состояние падения и в итоге должен прийти на опорную грань.

### Смена формы во время специальных состояний Triangle
- При смене формы во `freeze`:
  - freeze снимается;
  - ориентация сбрасывается;
  - заряд не тратится;
  - новая форма сразу переходит к своим правилам.
- При смене формы во время `dash`:
  - движение по заданной dash-траектории сохраняется;
  - но новая форма уже не разрушает breakable-объекты и не сохраняет спец-свойства dash.

## Square — канон
### Базовая роль формы
Square — форма с `attach`, `trail-resource` и `rollover`.

### Коллизия и поворот
- Коллайдер Square всегда квадратный.
- Реальный поворот Square учитывается.
- Attach к потолку — полноценный канон.

### Attach
- Attach выполняется через удержание `K`.
- Attach возможен к валидной поверхности даже без готового trail.
- Если attach начался на валидной поверхности, trail начинает строиться.
- Если на поверхности уже есть trail, Square может attach’иться к нему.
- Attach-compatible поверхности/объекты:
  - пол;
  - стены;
  - потолок;
  - наклоны;
  - moving platforms;
  - trigger platforms;
  - специальные совместимые поверхности.
- В будущем могут появиться поверхности, к которым attach невозможен, но не в текущем прототипе.

### Trail-resource
- У Square нет старой модели charges.
- Основная ресурсная модель — `trail-resource`.
- Ресурс расходуется по расстоянию, пройденному по поверхности в attach.
- Если Square стоит на trail и не движется, ресурс не расходуется.
- Если trail-resource заканчивается:
  - Square может стоять;
  - но не может строить новый trail.

### Trail как след на поверхности
- Trail отображается на поверхности.
- Trail глобальный.
- Если игрок начинает восстановление trail, старый trail стирается глобально.
- Trail может существовать на движущихся объектах и двигаться вместе с ними.
- Trail сохраняется, пока игрок не восстановит ресурс автоматически или вручную.

### Восстановление trail-resource
- Автовосстановление работает только вне attach.
- Ручное восстановление — по `O`.
- Оба режима действуют последовательно, от старого участка trail к новому.
- Если игрок начал новый attach, восстановление останавливается.
- Во время attach восстановление trail недоступно.

### Attach-jump с возвратом
- Пока удерживается attach, нажатие `Jump` запускает специальный attach-jump.
- Прыжок идёт перпендикулярно поверхности.
- Высота прыжка уменьшенная и фиксированная.
- До возврата должна читаться визуальная связь с trail.
- Если attach удерживается, Square возвращается в ту же attach-зону/точку, но с учётом её актуального положения.
- Возврат идёт как `натягивание связи / резинки`.
- Если attach был отпущен во время прыжка, Square отцепляется и переходит в свободное падение.
- Этот прыжок позволяет взаимодействовать с предназначенными для этого движущимися объектами:
  - объект может сдвигаться на фиксированное расстояние;
  - при возврате Square должен прийти к текущей поверхности объекта, а не в старые мировые координаты.

### Rollover
- `Square External-Corner Rollover` обязателен уже в первом прототипе.
- Rollover стартует из attach:
  - игрок удерживает attach;
  - игрок двигается к внешнему краю поверхности;
  - при валидных условиях rollover стартует автоматически.
- Если после rollover attach на новой поверхности невозможен, Square должен по той же траектории вернуться обратно без смещения.

### Смена формы во время Square state
- При смене формы во время attach:
  - trail остаётся;
  - attach сразу сбрасывается;
  - специфические состояния Square обнуляются;
  - новая форма дальше падает/едет/стоит по своим правилам.

## Wind zone — канон
- Wind zone входит в обязательный состав test scene.
- Ветер влияет на все формы, но не одинаково:
  - Ball сдувает сильнее всего;
  - Triangle — сильнее, чем Square, но слабее, чем Ball;
  - Square — слабее всего;
  - Square в attach ветер не сдувает вообще.
- Ветер влияет на прыжок и падение, меняя траекторию.
- Для Triangle ветер замедляет dash; после окончания dash он влияет уже как на обычный полёт/движение формы.

## Moving platform / overlap zone platform — канон
- В первой версии moving platform и trigger platform обязательны.
- Они должны возить игрока как опорная поверхность.
- Square может attach’иться к ним, если они attach-compatible.
- Trail может существовать на них и двигаться вместе с ними.

## UI — канон прототипа
### Правый нижний угол
- Показывается текущая форма.
- Показывается, какая форма будет следующей/предыдущей по `Q / E`.

### Верхняя часть экрана
- Для Ball — ресурсный UI пустой.
- Для Triangle — `3` сегмента/иконки зарядов.
- Для Square — `progress bar` с сегментами для trail-resource.

### Debug UI
- Debug UI входит в прототип.
- create/init window пока вынесено за скобки.

## То, что исключено из текущего scope
Не входит в текущий прототип:
- расширенный UI-framework;
- start window;
- сохранения;
- мета-прогресс;
- сюжет;
- звук;
- сложная анимационная система.

При этом прототип должен закладывать основу, чтобы в будущем можно было безболезненно добавить VFX, анимации и juice.

## Правило параметризации
Все критичные тайминги, силы и ограничения должны быть параметрами в геймдизайнерских единицах:
- время в секундах;
- расстояние;
- скорость;
- сила;
- вес;
- длины окон (`buffer`, `coyote`, hit pause и т. д.);
- длительность трансформации;
- скорость расхода trail;
- параметры ветра;
- параметры прыжка;
- параметры смерти и респавна;
- другие аналогичные величины.

# The Form — карта канона после опроса

Дата фиксации: 2026-03-25
Статус: рабочий канонический слой для переписывания документации

## 1. Новый source of truth

При конфликте источников истиной считается следующий порядок:

1. новые зафиксированные решения пользователя в текущем опросе;
2. новая MD-документация, собранная на основе этих решений;
3. старые MD и DOCX только как historical/reference layer;
4. старые статусы `Completed / In Progress / В работе` не считаются доказательством актуальности.

## 2. Что теперь является каноном

### 2.1. Архитектурный канон прототипа

Канонично:
- проект делается как `Phaser-native`, `docs-first`, `prefab-by-code-first`, `TypeScript-first`;
- TypeScript допускается только там, где редакторная / prefab-based реализация начинает ломать механику или делает её слишком грязной;
- физическая модель: `custom platformer`, не `Box2D / Physics World`;
- один `pf_player`, внутри которого три формы: `Ball / Triangle / Square`;
- формы доступны с начала test scene;
- стартовая форма — `Ball`;
- form switching: `Q/E`, циклическая цепочка `Ball -> Triangle -> Square -> Ball`, переключение доступно везде;
- у переключения есть короткое состояние трансформации с блокировкой повторного переключения;
- новый хитбокс формы включается в конце трансформации;
- если новая форма не помещается, переключение отменяется.

### 2.2. Общие системные правила

Канонично:
- `WASD` — движение;
- `Space` — jump;
- `K` — единая context ability button;
- удержание `K` у `Square` — attach;
- `O` — regen trail / regen triangle charges;
- для всех форм обязательны:
  - input buffer;
  - coyote time;
  - air control;
- dynamic jump height применяется только к обычному прыжку `Ball` и `Square`;
- урон/смерть: короткая death pause -> snap teleport to checkpoint;
- checkpoint хранит только позицию;
- после смерти игрок возрождается в `Ball`;
- после смерти все ресурсы и все оставленные следы/состояния игрока сбрасываются.

### 2.3. Канон visual marker / точки приложения

Канонично:
- существует единая для всех форм игровая системная сущность: visual marker / точка приложения;
- marker всегда видим поверх фигуры;
- marker одинаков по принципу для всех форм;
- marker влияет на поведение и на читаемость управления;
- marker двигается плавно, с промежуточными положениями и инерцией даже на клавиатуре;
- при отсутствии ввода marker возвращается в центр;
- у `Triangle` текущая ориентация связана с ведущим углом и marker.

### 2.4. Ball — каноничный контракт

Канонично:
- `Ball` — дефолтная форма;
- активная способность по `K` — ускорение;
- ускорение работает на земле;
- ускорение стартует как импульс и дальше переходит в удерживаемое ускоренное движение;
- у `Ball` нет ресурсов;
- rebound активируется повторным нажатием `Jump` с forgiveness/input buffer;
- от стен rebound имеет upward assist correction;
- от пола и потолка используется принцип отражения по траектории;
- hit pause срабатывает только если rebound успешно активирован;
- rebound-chain не ограничен искусственным капом: игрок может распрыгиваться бесконечно, если выдерживает тайминг и геометрию;
- обычный прыжок = высота 1;
- rebound-прыжки = усиленная высота 2 и дальнейшее распрыгивание.

Коллизия:
- коллайдер `Ball` всегда круглый.

### 2.5. Triangle — каноничный контракт

Канонично:
- `Triangle` реально учитывает ориентацию;
- коллайдер должен соответствовать форме треугольника и его повороту;
- обычный jump у `Triangle` отдельный: начинается с резкого разворота на месте и отталкивания от поверхности;
- высота и сила обычного triangle jump фиксированы;
- повторный `Jump` в воздухе включает `freeze`;
- `freeze` сам по себе заряд не тратит;
- dash по `K` тратит заряд;
- зарядов `3`;
- dash возможен:
  - с пола;
  - из воздуха после `freeze`;
  - из воздуха без `freeze`;
- dash без freeze берёт направление из текущей ориентации `Triangle`;
- во время freeze по повторному `Jump` новый freeze не запускается — треугольник просто падает;
- после dash в воздухе снова можно войти во freeze;
- `Triangle` может ломать только специальные breakable-объекты;
- после пробития breakable-объекта dash продолжается;
- может пробивать несколько breakable-объектов подряд;
- если ударился в непробиваемую поверхность, застревает углом;
- после нажатия `Jump` отпрыгивает по нормали поверхности;
- затем падает и должен в итоге устойчиво лечь на грань, а не оставаться на угле;
- каждая грань может быть опорной поверхностью.

Заряды:
- восстанавливаются по `O`;
- восстановление доступно только стоя на земле;
- восстановление не постепенное, а мгновенное после задержки/анимации;
- в UI показываются как 3 отдельные иконки/сегмента.

### 2.6. Square — каноничный контракт

Канонично:
- `Square` использует attach-механику;
- attach возможен к валидной поверхности даже без готового trail;
- при attach trail начинает строиться;
- если trail уже существует на поверхности, к нему можно attach'иться;
- attach-compatible поверхности в прототипе:
  - пол;
  - стены;
  - потолок;
  - наклоны;
  - moving platforms;
  - trigger platforms;
  - специальные объекты;
  - breakable-совместимые поверхности, если это будет отдельно разрешено уровнем;
- коллайдер `Square` квадратный;
- для `Square` важен реальный поворот, а не только визуальный.

Trail-resource:
- старые `charges` для `Square` отменены;
- основной ресурс — trail-resource;
- ресурс тратится по пройденной дистанции вдоль поверхности;
- если `Square` стоит, ресурс не расходуется;
- если ресурс закончился, `Square` может стоять, но не может строить новый trail;
- trail глобальный;
- trail живёт, пока не будет собран/восстановлен;
- восстановление trail идёт от старого к новому;
- trail может существовать на движущихся объектах и двигаться вместе с ними.

Regen:
- auto regen работает только вне attach;
- ручной regen по `O` работает только вне attach;
- regen идёт от старого к новому;
- если игрок начал новый attach, regen останавливается.

Attach-jump:
- запускается `Jump`, пока удерживается attach;
- квадрат делает уменьшенный фиксированный прыжок перпендикулярно поверхности;
- визуально остаётся связь с trail;
- если attach удерживается, квадрат возвращается назад как натягивание резинки;
- возвращение идёт не в старые мировые координаты, а в актуальное положение attach-point / attach-zone;
- если attach отпущен, квадрат отцепляется и переходит в свободное падение.

Rollover:
- `Square External-Corner Rollover` обязателен уже в первом прототипе;
- стартует автоматически из attach при правильном движении в край и удержании attach;
- attach к потолку полноценный;
- если после rollover attach на новой поверхности невозможен, квадрат возвращается по обратной траектории без смещений.

### 2.7. Wind / world interaction

Канонично:
- wind влияет на все формы;
- сильнее всего wind сдувает `Ball`;
- затем `Triangle`;
- слабее всего `Square`;
- `Square` в attach не сдувается вообще;
- wind меняет траекторию прыжка и падения;
- wind замедляет dash `Triangle`, после окончания dash влияние продолжается уже по правилам формы/движения.

### 2.8. Level objects / test scene

Каноничный минимум test scene:
- ровный пол;
- стены;
- потолок;
- наклоны;
- внешний угол для square rollover;
- hazard;
- checkpoint;
- finish / exit;
- wind zone;
- moving platform;
- trigger platform;
- узкие вертикальные зоны для wall-bounce `Ball`;
- breakable wall/object для `Triangle`.

Moving / trigger platforms:
- являются полноценной опорной поверхностью;
- могут взаимодействовать с `Square attach`;
- могут хранить на себе trail;
- trail двигается вместе с платформой.

### 2.9. UI-канон для прототипа

Канонично:
- справа внизу UI показывает:
  - текущую форму;
  - форму на `Q`;
  - форму на `E`;
- сверху:
  - для `Ball` ресурсный UI пустой;
  - для `Triangle` показываются 3 charge icons/segments;
  - для `Square` показывается progress bar с сегментами trail-resource;
- debug UI нужен;
- стартовое окно в scope первого прототипа не входит.

### 2.10. Параметризация

Канонично:
- все силы, дистанции, тайминги, веса и коэффициенты должны быть параметрами;
- параметры должны быть в геймдизайнерских единицах, а не в абстрактных скрытых числах;
- приоритет единиц:
  - секунды;
  - расстояние;
  - скорость;
  - вес;
  - количество зарядов/сегментов;
- в будущем параметры должны настраиваться без болезненного переписывания логики.

## 3. Что больше не считается каноном и должно быть переписано

### 3.1. Устаревшие элементы по Square

Устарело и не должно больше считаться source of truth:
- старое описание `Square` через charges как основную модель ресурса;
- любые старые тексты, где trail не является основным ресурсом;
- любые старые формулировки, где нет attach-jump с возвратом к trail;

### 3.2. Устаревшие элементы по Triangle

Устарело:
- старые формулировки, где dash требует charge/freeze цепочку в обязательном порядке;

### 3.3. Устаревшие элементы по Ball

Требуют переписывания:
- любые старые описания `Ball`, где rebound не опирается на повторный `Jump`;
- любые описания, где upward assist на wall-bounce отсутствует;
- любые формулировки, не различающие первую и вторую высоту прыжка.

### 3.4. Устаревшие элементы по UI

Устарело:
- старые UI-описания, жёстко завязанные на прежнюю модель charges для `Square`;
- любые старые UI-контракты, где нет правого нижнего form-switch preview;
- любые старые слои, где верхний UI считается общим одинаковым ресурсным интерфейсом для всех форм.

# The Form — Prototype Implementation Order

Статус: canonical draft  
Дата: 2026-03-25

## 1. Назначение документа
Этот документ фиксирует **рекомендуемый порядок сборки прототипа `The Form` в `Phaser`**.

Его задача:
- не начинать с самых тяжёлых механик раньше времени;
- сохранить `Phaser-native / docs-first / Codex-first / scene-first / TypeScript-first` подход;
- собирать прототип слоями, где каждый следующий шаг опирается на уже проверенную базу;
- заранее разделить, что делаем сначала ради устойчивого production path, а что оставляем на later slice.

Этот документ описывает именно **implementation order**, а не весь канон механик. Источником истины по механикам остаются:
- `the_form_prototype_decisions_ru.md`;
- релевантные `feature_*` документы;
- `the_form_test_scene_spec_ru.md`.

---

## 2. Главный принцип порядка
Хотя по игровой сложности `Triangle` и `Square` являются самыми рискованными формами, **реальный порядок реализации не должен начинаться с них**.

Для нового прототипа принят такой принцип:

1. сначала собрать **общую scene/config/data/Codex-base основу**;
2. затем собрать **дефолтную Ball-ветку** как самый удобный carrier для проверки базовых систем;
3. затем собрать **общую инфраструктуру form switching / UI / marker / scene objects**;
4. только потом переходить к `Triangle`;
5. и после этого — к `Square`.

Причина:
- `Triangle` и особенно `Square` завязаны на уже готовые общие системы;
- если начинать с них, проект почти сразу уйдёт в сложную геометрию без проверенной базы;
- `Ball` даёт самый дешёвый способ проверить: input, jump, death, checkpoint, platforms, camera, wind, transform flow.

---

## 3. Implementation strategy summary

### 3.1. Приоритет order
Рекомендуемый порядок сборки:

1. **Project shell + test scene foundation**
2. **Common player shell**
3. **Common input + timers + marker**
4. **Ball base**
5. **Camera**
6. **Checkpoint / hazard / moving platform / trigger platform / wind**
7. **Form switching shell + minimal UI**
8. **Triangle**
9. **Breakable objects**
10. **Square attach baseline**
11. **Square trail resource + regen**
12. **Square attach-jump with return**
13. **Square rollover + rollback**
14. **Pass of cleanup / parameter surfacing / debug pass**

### 3.2. Что нельзя делать раньше времени
Не рекомендуется до готовности базовых слоёв:
- сразу строить `Square rollover`;
- сразу делать полный `Triangle freeze + dash + stuck-in-wall`;
- сразу пытаться идеально тюнить wind, camera и form switching;
- раньше времени строить красивые VFX/UI вместо gameplay proof.

---

## 4. Фаза 0 — Project shell
### Цель
Создать чистую основу проекта и test scene, не влезая сразу в сложную механику.

### Что делаем
- создаём новый проект `Phaser` под прототип;
- заводим базовые папки ресурсов;
- создаём каноническую `test scene`;
- создаём placeholder-спрайты/формы, если финальных ещё нет;
- задаём scene/view setup на минимальном уровне.

### Что делаем через scene/config/data wiring
- folders/resources;
- scene layers;
- placement базовой геометрии;
- baseline instances;
- initial camera/view settings.

### Exit criteria
- проект открывается без legacy-хвостов;
- есть одна каноническая `test scene`;
- в scene уже есть заготовки для базовых проверок.

---

## 5. Фаза 1 — Common player shell
### Цель
Создать один `pf_player` как общий носитель трёх форм.

### Что делаем
- создаём `pf_player`;
- вводим текущую форму как state/mode;
- создаём базовые переменные общих систем;
- делаем spawn в `Ball` как дефолтную форму;
- подключаем placeholder визуал и базовый draw.

### На этом этапе пока НЕ делаем
- сложный Triangle behavior;
- Square attach;
- rollover;
- сложный UI.

### Exit criteria
- в scene стабильно существует один игрок;
- он спавнится как `Ball`;
- общие переменные и timers инициализируются предсказуемо.

---

## 6. Фаза 2 — Common input, timers, marker
### Цель
Собрать общую платформу ввода и общие системные таймеры раньше механик форм.

### Что делаем
- `WASD`;
- `Space`;
- `K`;
- `O`;
- `Q/E`;
- общие timers:
  - coyote time;
  - jump input buffer;
  - transformation lock;
  - death pause;
- visual marker как always-visible элемент.

### Порядок внутри фазы
1. input map;
2. buffer/forgiveness timers;
3. marker movement with inertia;
4. marker return to center;
5. debug-visible marker verification.

### Предпочтительный подход
- сначала `scene/config wiring`, если логика остаётся читаемой;
- marker inertia — кандидат на узкий `TypeScript`, если в `scene/config wiring` станет хрупко.

### Exit criteria
- input стабильно читается;
- marker ведёт себя одинаково для всех форм;
- общие таймеры работают независимо от конкретной формы.

---

## 7. Фаза 3 — Ball base
### Цель
На Ball проверить базовую платформенную читаемость и общий movement-feel.

### Что делаем сначала
- ground movement;
- обычный jump;
- coyote time;
- jump buffer;
- dynamic jump height;
- air control.

### Что делаем потом
- boost по `K` на земле;
- rebound по `Space` на поверхностях;
- hit pause только при валидном rebound;
- wall upward assist;
- stronger rebound chain logic.

### Почему Ball раньше Triangle/Square
Потому что Ball:
- дефолтная форма респавна;
- даёт дешёвую проверку общего platformer-feel;
- позволяет проверить camera / death / checkpoint / wind раньше сложных угловых механик.

### Exit criteria
- Ball уже ощущается как играбельная форма;
- можно двигаться, прыгать, падать, умирать и возвращаться на checkpoint;
- rebound не ломает базовую геометрию scene.

---

## 8. Фаза 4 — Camera
### Цель
Поставить камеру рано, но только после того, как есть хоть какой-то настоящий movement.

### Что делаем
- follow camera;
- freedom frame / deadzone;
- lower-center bias;
- минимальную плавность.

### Не делаем пока
- сложные camera states;
- кинематографические переходы;
- крупный camera polish.

### Exit criteria
- Ball играется в scene с читаемой камерой;
- игрок может смещаться внутри frame без постоянного дёрганья камеры.

---

## 9. Фаза 5 — World interaction baseline
### Цель
Собрать объекты мира, которые нужны почти всем формам.

### Что делаем
- checkpoint;
- hazard;
- moving platform;
- trigger platform;
- wind zone.

### Почему здесь, а не позже
Потому что эти объекты понадобятся всем трём формам и должны быть проверены на Ball до сложных форм.

### Exit criteria
- death/reset cycle работает;
- платформы двигаются и возят игрока;
- wind влияет на Ball;
- scene уже похожа на системный testbed.

---

## 10. Фаза 6 — Form switching shell + minimal UI
### Цель
Собрать форму как системный контракт до внедрения Triangle/Square.

### Что делаем
- `Q/E` cycle;
- transformation state;
- repeated-switch lock;
- проверку валидного пространства для новой формы;
- отмену switch при невалидном пространстве;
- minimal form UI справа внизу;
- верхний UI shell.

### Важно
На этом этапе можно ещё не иметь всей финальной логики `Triangle/Square`, но contract switching уже должен существовать.

### Exit criteria
- можно переключаться между формами без развала player core;
- трансформация блокирует повторный switch;
- неверный switch корректно отменяется.

---

## 11. Фаза 7 — Triangle baseline
### Цель
Собрать самую рискованную форму после того, как общий каркас уже стабилен.

### Порядок внутри фазы
1. real orientation baseline;
2. special jump through rotation;
3. grounded support on any face;
4. airborne control of leading corner;
5. freeze;
6. dash;
7. dash charges;
8. recharge on `O` while grounded;
9. dash without freeze from valid states;
10. stuck-in-solid behavior;
11. jump-away by surface normal.

### Почему Triangle раньше Square
Потому что `Triangle` проверяет:
- real orientation;
- shaped collision;
- special jump logic;
- dash state;
- state transitions under transform;
без world-trail persistence, которая делает Square ещё дороже.

### Где возможен узкий TypeScript раньше всего
- orientation / leading corner logic;
- shaped collision handling;
- dash vector selection.

### Exit criteria
- Triangle играется как отдельная форма;
- charges / freeze / dash работают;
- после жестких ситуаций треугольник приходит на грань, а не зависает случайно.

---

## 12. Фаза 8 — Breakable baseline
### Цель
Добавить breakable-объекты сразу после Triangle, а не до него.

### Что делаем
- объекты, которые ломаются только от `Triangle dash`;
- простое исчезновение;
- простую анимацию/эффект;
- превращение участка в проходимый.

### Exit criteria
- Triangle корректно взаимодействует с breakable;
- другие формы не получают accidental special behavior.

---

## 13. Фаза 9 — Square attach baseline
### Цель
Собрать Square не с rollover, а с attach-основы.

### Что делаем сначала
- квадратная форма с реальным поворотом;
- attach к валидной поверхности;
- пол / стены / потолок / наклоны;
- attach-compatible moving objects;
- detach при выходе из состояния.

### Не делаем пока
- полный trail economy;
- tether return;
- rollover.

### Exit criteria
- Square умеет стабильно attachиться к world surfaces;
- переходы floor / wall / ceiling уже не разваливают базовую логику.

---

## 14. Фаза 10 — Square trail resource + regen
### Цель
Добавить мировое состояние trail после того, как attach уже сам по себе работает.

### Что делаем
- trail generation while attached;
- расход по дистанции;
- global trail state;
- attach to existing trail;
- auto regen outside attach;
- manual regen on `O`;
- erase from oldest to newest;
- stop regen when new attach starts;
- UI progress bar.

### Exit criteria
- trail читаемо живёт в мире;
- regeneration не конфликтует с новым attach;
- UI отражает ресурс без двусмысленности.

---

## 15. Фаза 11 — Square attach-jump with return
### Цель
Добавить привязанный прыжок только после стабилизации attach и trail.

### Что делаем
- jump while holding attach;
- fixed reduced perpendicular jump;
- tether-like visual link;
- return to current valid attach location, not stale world coordinates;
- detach if attach released;
- support for moving compatible surfaces.

### Почему не раньше
Потому что attach-jump зависит сразу от:
- attach baseline;
- trail state;
- moving surface support;
- return target validity.

### Exit criteria
- Square может прыгнуть от trail и вернуться обратно без входа в объект;
- moving object case не ломает return.

---

## 16. Фаза 12 — Square rollover + rollback
### Цель
Добавить самую дорогую механику уже на почти готовую поверхность Square.

### Что делаем
- rollover через внешний угол;
- preview / start conditions;
- переход attach на новую поверхность;
- rollback по той же траектории, если новая attach-поза невалидна.

### Почему это почти последняя core-фаза
Потому что rollover зависит от:
- real square rotation;
- surface attach correctness;
- corner geometry;
- target validity checks;
- rollback logic.

### Где узкий TypeScript почти наверняка оправдан
- corner state evaluation;
- rollover trajectory;
- rollback validation.

### Exit criteria
- внешний угол проходится предсказуемо;
- невалидный исход возвращает квадрат обратно без дрейфа.

---

## 17. Фаза 13 — Integration pass
### Цель
Проверить, что формы и мир взаимодействуют друг с другом по канону, а не только по отдельности.

### Что проверяем
- смерть/респавн из всех форм;
- сброс ресурсов и следов;
- switching во время активных состояний;
- moving/trigger platform interactions;
- wind interactions;
- UI correctness per form;
- transformation collision validity.

### Exit criteria
- test scene можно использовать как главный proof environment;
- все формы проходят базовый системный smoke test.

---

## 18. Фаза 14 — Parameter surfacing and debug pass
### Цель
После того как механика уже работает, вынести всё нужное в настраиваемые параметры и собрать удобный debug слой.

### Что делаем
- выносим силы/времена/дистанции в design-facing параметры;
- сверяем названия с `parameters_registry`;
- добавляем debug UI только в том объёме, который помогает тюнингу;
- не строим giant debug framework.

### Exit criteria
- ключевые параметры доступны для настройки;
- прототип можно тюнить без переписывания core behavior.

---

## 19. Practical sequencing notes
### 19.1. Что можно делать параллельно
Допустимо параллелить:
- scene geometry polishing;
- placeholder art;
- UI mock setup;
- parameter naming.

Но не стоит параллелить несколько тяжёлых core-механик одновременно.

### 19.2. Что замораживать по ходу
После завершения фазы желательно считать её baseline до конца следующей тяжёлой фазы.

Например:
- сначала стабилизировали Ball;
- потом не возвращаемся его радикально ломать, пока не прошли базовый Triangle slice.

### 19.3. Когда возвращаться к rework
Возврат к предыдущему слою оправдан только если:
- новая форма вскрыла реальный дефект общего контракта;
- документированный канон требует пересмотра;
- без rework следующий шаг бессмысленен.

---

## 20. Итоговый recommended build order
В кратком виде:

1. Project shell + test scene
2. `pf_player` shell
3. common input/timers/marker
4. Ball base
5. camera
6. checkpoint/hazard/platforms/wind
7. form switching + minimal UI
8. Triangle
9. breakable
10. Square attach
11. Square trail/regeneration
12. Square attach-jump
13. Square rollover/rollback
14. integration pass
15. parameter/debug pass

Это и есть рекомендуемый порядок, который лучше всего соответствует:
- `Phaser-native` подходу;
- `prefab-by-code-first / TypeScript-first` реализации;
- одному `pf_player`;
- канонической `test scene`;
- снижению риска упереться в самую дорогую механику слишком рано.

# The Form — Test Scene Spec (RU)

## Статус документа
Canonical draft для нового прототипа `The Form`.

Этот документ фиксирует состав, назначение и правила использования **канонической test scene** для первого прототипа.

---

## 1. Назначение test scene

`test scene` — это не уровень кампании и не вертикальный срез с началом и концом.
Это **каноническая среда проверки механик**, в которой должны проверяться:

- базовое движение игрока;
- form switching;
- поведение `Ball`;
- поведение `Triangle`;
- поведение `Square`;
- взаимодействие форм с поверхностями;
- взаимодействие с `wind`, `hazard`, `checkpoint`;
- взаимодействие с `moving platform` и `trigger platform`;
- работа UI и marker в условиях реального теста.

Первая playable-сборка прототипа должна быть ориентирована именно на эту scene.

---

## 2. Общие принципы test scene

### 2.1. Главный принцип
Scene должна быть построена не как красивая сцена, а как **ясный набор испытательных секций**.

### 2.2. Читаемость важнее декора
На первом прототипе не требуется декоративное оформление.
Главная задача — чтобы было легко понять:

- где проверяется каждая механика;
- откуда начинать тест;
- где ожидается корректное поведение;
- где произошёл сбой.

### 2.3. Один scene — много секций
Первая версия использует **одну test scene**, в которой собраны все обязательные тестовые зоны.

### 2.4. Минимум лишнего шума
В test scene не должно быть:

- сюжетных объектов;
- лишнего UI;
- декоративных анимаций, которые мешают считывать механику;
- неоправданных сложных scripted events.

---

## 3. Канонический состав test scene

В первой канонической версии test scene должны присутствовать все перечисленные ниже зоны.

### 3.1. Стартовая безопасная площадка
Назначение:

- спавн игрока;
- первичная проверка движения;
- первичная проверка form switching;
- первичная проверка marker и UI.

Требования:

- ровная горизонтальная поверхность;
- достаточно свободного места слева и справа;
- отсутствие hazards в непосредственной близости;
- игрок стартует в форме `Ball`.

### 3.2. Секция обычного движения
Назначение:

- проверить разгон / торможение / air control;
- проверить обычный jump;
- проверить `coyote time`;
- проверить `input buffer`;
- проверить dynamic jump height у `Ball` и `Square`.

Требования:

- длинный ровный пол;
- небольшой разрыв между платформами;
- несколько разных по длине платформ.

### 3.3. Секция Ball wall-bounce
Назначение:

- проверить rebound от стен;
- проверить upward correction от стен;
- проверить rebound chain;
- проверить hit pause при успешном rebound;
- проверить, что игрок может забираться наверх между узкими стенами.

Требования:

- минимум один узкий вертикальный колодец между двумя стенами;
- одна широкая вертикальная стена для одиночного bounce-теста;
- безопасная зона для повторных попыток.

### 3.4. Секция Ball floor/ceiling rebound
Назначение:

- проверить rebound от пола;
- проверить rebound от потолка;
- проверить правило «угол падения равен углу отражения» для вертикальных поверхностей контакта;
- проверить вторую высоту rebound-chain.

Требования:

- участок пола и низкий потолок;
- геометрия, позволяющая многократно проверять rebound вверх-вниз.

### 3.5. Секция Triangle jump / freeze / dash
Назначение:

- проверить особый jump треугольника;
- проверить freeze по повторному нажатию `Jump` в воздухе;
- проверить поворот по направлению ввода;
- проверить dash по `Ability`;
- проверить dash с земли;
- проверить dash из воздуха через freeze;
- проверить dash из воздуха без freeze.

Требования:

- открытое пространство для воздушных манёвров;
- несколько удобных поверхностей для старта dash;
- достаточный обзор траектории.

### 3.6. Секция Triangle breakable test
Назначение:

- проверить разрушение `breakable`-объектов только через dash треугольника;
- проверить, что после разрушения область становится проходимой;
- проверить, что `Ball` и `Square` не ломают такие объекты;
- проверить поведение при прохождении через несколько breakable-поверхностей подряд.

Требования:

- минимум одна одиночная breakable-стенка;
- минимум одна последовательность из нескольких breakable-объектов.

### 3.7. Секция Triangle non-breakable impact
Назначение:

- проверить, что при ударе в непробиваемую поверхность треугольник застревает углом;
- проверить, что по `Jump` он отпрыгивает по нормали поверхности;
- проверить, что потом он приходит в устойчивое положение на грань, а не остаётся на углу.

Требования:

- непробиваемая стена;
- безопасная геометрия для повторных попыток.

### 3.8. Секция Square attach basics
Назначение:

- проверить attach к полу;
- проверить attach к стенам;
- проверить attach к потолку;
- проверить attach к наклонным поверхностям;
- проверить расход trail-ресурса по дистанции.

Требования:

- одна горизонтальная поверхность;
- одна вертикальная стена;
- один потолок, пригодный для attach;
- минимум один slope.

### 3.9. Секция Square trail behavior
Назначение:

- проверить, что при attach trail строится по валидной поверхности;
- проверить attach к уже существующему trail;
- проверить остановку trail-регена при начале нового attach;
- проверить авто-реген вне attach;
- проверить ручной regen по `O`;
- проверить, что реген идёт от старого к новому.

Требования:

- достаточно длинные attach-compatible поверхности;
- понятная визуальная зона считывания trail.

### 3.10. Секция Square attach-jump
Назначение:

- проверить attach-jump по `Jump` при удержании attach;
- проверить уменьшенный фиксированный прыжок перпендикулярно поверхности;
- проверить возврат по «резинке» обратно к trail;
- проверить, что при отпускании attach квадрат отцепляется и падает.

Требования:

- минимум одна поверхность для attach-jump без подвижных объектов;
- свободное пространство рядом с поверхностью.

### 3.11. Секция Square rollover
Назначение:

- проверить rollover через внешний угол;
- проверить preview/start contract rollover;
- проверить успешный переход на новую поверхность;
- проверить возврат по обратной траектории, если attach на новой поверхности невозможен.

Требования:

- минимум один чистый внешний угол floor→wall;
- минимум один чистый внешний угол wall→ceiling;
- минимум одна ситуация, где rollover валиден частично, но завершение attach должно провалиться и квадрат обязан вернуться назад.

### 3.12. Секция hazards
Назначение:

- проверить death pause;
- проверить teleport на checkpoint;
- проверить полный reset состояния игрока;
- проверить, что следы / состояния / ресурсы сбрасываются корректно.

Требования:

- минимум одна hazard-зона;
- безопасная позиция checkpoint перед ней.

### 3.13. Секция checkpoint
Назначение:

- проверить активацию checkpoint;
- проверить respawn именно в сохранённой позиции;
- проверить respawn в дефолтной форме `Ball`.

Требования:

- минимум один checkpoint в середине scene;
- желательно ещё один checkpoint глубже по комнате для повторной проверки.

### 3.14. Секция wind zone
Назначение:

- проверить влияние ветра на все формы;
- проверить, что `Ball` сдувает сильнее всего;
- проверить, что `Triangle` сдувает средне;
- проверить, что `Square` сдувает слабее всего;
- проверить, что `Square` в attach ветром не сдувается;
- проверить, что wind меняет траекторию прыжка и падения;
- проверить замедление dash у Triangle.

Требования:

- отдельная wind zone в читаемой секции;
- достаточно пространства для входа и выхода из зоны ветра.

### 3.15. Секция moving platform
Назначение:

- проверить, что игрок корректно ездит на moving platform;
- проверить взаимодействие всех форм с движущейся опорой;
- проверить attach квадратом к moving platform;
- проверить trail на движущейся платформе.

Требования:

- минимум одна автоматически движущаяся платформа;
- траектория должна быть простой и читаемой.

### 3.16. Секция trigger platform
Назначение:

- проверить платформу, которая начинает движение по триггеру;
- проверить взаимодействие игрока с ней после активации;
- проверить attach и trail, если такая платформа attach-compatible.

Требования:

- минимум одна trigger platform;
- должен существовать понятный способ её активации.

# The Form — Feature Doc: Input and Marker

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`
- Роль документа: зафиксировать общий input contract и канон visual marker / точки приложения

---

## 2. Назначение системы
Этот слой фиксирует две вещи:
- обязательную схему управления прототипом;
- общую для всех форм систему visual marker, которая показывает направление намерения игрока.

Visual marker — не косметический debug-элемент. Для прототипа это полноценный, всегда видимый игровой элемент.

---

## 3. Общий input contract
### 3.1 Базовые кнопки
- `W / A / S / D` — движение
- `Space` — `Jump`
- `K` — контекстная `Ability`
- удержание `K` — `Attach` у Square
- `O` — восстановление trail у Square / зарядов у Triangle
- `Q / E` — переключение формы

### 3.2 Единая ability-кнопка
`K` — единая контекстная ability-кнопка для всех форм:
- у `Ball` — ускорение / boost;
- у `Triangle` — dash;
- у `Square` — attach при удержании.

### 3.3 Общие системные правила ввода
Для прототипа обязательны:
- input buffer;
- coyote time;
- air control.

### 3.4 Dynamic jump height
Dynamic jump height канонически применяется:
- к обычному jump у `Ball`;
- к обычному jump у `Square`.

Для Triangle обычный jump особый и не использует этот же контракт в прямом виде.

---

## 4. Visual marker / точка приложения
### 4.1 Каноническое понимание
Visual marker — это общая системная концепция для `Ball / Triangle / Square`.

Он:
- показывает направление намерения игрока;
- всегда видим поверх фигуры;
- одинаков по базовой логике для всех форм;
- влияет на читаемость управления;
- влияет на поведение форм;
- в будущем может влиять и на анимации/деформации.

### 4.2 Исторический слой
В старых документах marker / точка приложения уже присутствовал как visual/input-концепт.

Новый канон уточняет это:
- это не просто визуальная подсказка;
- это полноценная часть игрового контракта и поведения персонажа.

---

## 5. Поведение marker
### 5.1 Видимость
Marker должен:
- быть видимым всегда;
- отображаться поверх текущей формы;
- не исчезать при обычной игре.

### 5.2 Возврат в нейтраль
Если игрок перестал давать направляющий ввод:
- marker возвращается в центр фигуры.

### 5.3 Движение
Marker не должен телепортироваться только между жёсткими 8 направлениями.

Канон:
- он двигается внутри фигуры плавно;
- имеет промежуточные положения;
- имеет инерцию даже на клавиатурном вводе.

### 5.4 Общая форма поведения
Marker должен ощущаться как маленькая внутренняя масса / фокус управления, а не как сухой UI-курсор.

---

## 6. Связь marker с формами
### 6.1 Ball
У Ball marker помогает читать:
- направление движения;
- намерение на rebound / bounce flow;
- общее состояние контроля формы.

### 6.2 Triangle
У Triangle marker особенно важен:
- у Triangle всегда есть ведущий угол;
- текущая ориентация Triangle и marker связаны;
- dash из воздуха без freeze берёт направление из текущей ориентации Triangle;
- эта текущая ориентация читается через ведущий угол и marker.

### 6.3 Square
У Square marker помогает читать:
- движение по attach-поверхности;
- направление намерения игрока на маршруте;
- общее положение игрока в контексте attach / rollover / attach-jump.

---

## 7. Input forgiveness systems
### 7.1 Input buffer
Input buffer обязателен для всех форм и должен прощать раннее нажатие прыжка.

Это означает:
- если игрок нажал `Jump` чуть раньше контакта с валидной поверхностью, прыжок всё равно должен сработать в пределах окна forgiving input.

Применение:
- обычный jump;
- rebound Ball;
- attach-related jump сценарии Square там, где это уместно по форме.

### 7.2 Coyote time
Coyote time обязателен для всех форм.

Это означает:
- если игрок уже начал сходить с платформы, но окно coyote time ещё открыто, jump всё ещё разрешён.

### 7.3 Air control
Игрок должен сохранять возможность корректировать положение персонажа в воздухе.

---

## 8. Regen input
### 8.1 Кнопка `O`
`O` — общая специальная кнопка восстановления form-specific ресурса.

### 8.2 Triangle
У Triangle `O`:
- работает стоя на земле;
- запускает мгновенное восстановление зарядов после задержки и анимации.

### 8.3 Square
У Square `O`:
- работает только вне attach;
- запускает восстановление trail-ресурса по каноническому правилу регена.

---

## 9. UI contract
### 9.1 Верхний UI
Верхний UI зависит от формы:
- `Ball` — ресурсный верхний UI пустой на этапе прототипа;
- `Triangle` — показываются 3 отдельных сегмента/иконки зарядов;
- `Square` — показывается `progress bar` с сегментами trail-ресурса.

### 9.2 Нижний UI
В правом нижнем углу показывается:
- текущая форма;
- что будет на `Q`;
- что будет на `E`.

### 9.3 Marker и UI
Marker не должен превращаться в замену UI-виджету. Он относится к телу персонажа и читается как часть самой формы.

---

## 10. Design-facing параметры
Все input- и marker-величины должны быть параметризованы.

Минимум параметров:
- длительность input buffer;
- длительность coyote time;
- скорость смещения marker;
- сила / коэффициент инерции marker;
- скорость возврата marker к центру;
- визуальный размер marker;
- отступ marker от границ формы;
- длительности задержек на regen-акции.

Все параметры задаются в реальных величинах:
- секунды;
- расстояния;
- размеры;
- скорости.

---

## 11. Что документ сознательно не описывает
Документ не уходит в:
- конкретную реализацию marker в scene/config wiring / TypeScript / Codex-slice orchestration;
- финальный арт / шейдеры marker;
- поздние эмоции / цветовые состояния Ball;
- финальную анимационную систему форм.

# The Form — Feature Doc: Form Switching

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`
- Роль документа: зафиксировать игровой и системный контракт переключения форм в новом Phaser-native / docs-first / prefab-by-code-first / TypeScript-first прототипе

---

## 2. Назначение системы
Form switching — это центральная связующая механика прототипа.

Её задача:
- позволять игроку быстро выбирать подходящую форму под геометрию и ситуацию;
- сохранять ощущение, что Ball / Triangle / Square — это один персонаж, а не три разных сущности;
- поддерживать вертикальный срез, где окружение требует чередовать формы, а не проходится одной формой по умолчанию.

Переключение формы не является косметической анимацией. Это базовая игровая система, через которую читается структура уровня и вся логика прототипа.

---

## 3. Основной контракт
### 3.1 Общая схема
- У игрока один `pf_player`.
- Внутри него есть три формы: `Ball`, `Triangle`, `Square`.
- Переключение циклично.
- Все три формы доступны с самого начала test scene.

### 3.2 Порядок форм
Каноническая цепочка:
- `Ball -> Triangle -> Square -> Ball`

Переключение работает в обе стороны:
- `Q` — переход в одну сторону по цепочке;
- `E` — переход в обратную сторону по цепочке.

### 3.3 Стартовая и respawn-форма
- Стартовая форма в test scene: `Ball`.
- Форма после смерти и respawn: `Ball`.

---

## 4. Input contract
### 4.1 Кнопки
- `Q / E` — переключение формы

### 4.2 Где разрешено переключение
Переключение формы разрешено:
- на земле;
- в воздухе;
- во время attach у Square;
- во время freeze у Triangle;
- во время dash у Triangle;
- во время активного движения любой формы.

### 4.3 Где запрещено повторное переключение
Повторное переключение запрещено только во время внутреннего состояния трансформации.

---

## 5. Состояние трансформации
### 5.1 Суть
Каждое переключение запускает короткое состояние трансформации:
- проигрывается короткая анимация / читаемый переход;
- повторное переключение на это время блокируется;
- новая форма считается окончательно активной только после завершения трансформации.

### 5.2 Hitbox rule
- Хитбокс новой формы включается в конце трансформации.
- До этого действует старый хитбокс / старая форма по правилу текущего implementation layer.

### 5.3 Fail rule
Если в целевой форме игрок не помещается:
- переключение отменяется;
- старая форма сохраняется;
- система не должна насильно выталкивать игрока в стороннюю позицию.

---

## 6. Правила переноса состояния между формами
### 6.1 Что сохраняется по умолчанию
По умолчанию при смене формы сохраняются:
- текущая скорость;
- текущее направление движения;
- положение visual marker;
- импульс движения, если он уже есть.

### 6.2 Что сильнее общего правила
Form-specific state reset rules сильнее общего правила переноса.

Это означает:
- Square может потерять attach-state, даже если скорость сохраняется;
- Triangle может потерять freeze/orientation-specific состояние, даже если общий импульс ещё есть;
- активный dash может превратиться в обычное движение новой формы без сохранения специальных свойств dash.

---

## 7. Form-specific transition rules
### 7.1 Из Square
Если игрок переключает форму во время attach Square:
- trail остаётся в мире;
- attach сразу сбрасывается;
- квадратные специфические состояния обнуляются;
- новая форма начинает вести себя по своим правилам;
- дальше игрок либо падает, либо движется, либо уже стоит на поверхности по общим правилам новой формы.

### 7.2 Из Triangle freeze
Если игрок переключает форму во время freeze Triangle:
- freeze снимается;
- ориентация Triangle-состояния сбрасывается;
- заряд dash не тратится;
- новая форма немедленно берёт управление на себя.

### 7.3 Из Triangle dash
Если игрок переключает форму во время dash Triangle:
- игрок продолжает движение по уже заданной dash-траектории;
- новая форма уже коллизится и ведёт себя как новая форма;
- специальные свойства dash больше не действуют;
- breakable-объекты больше не ломаются только из-за сохранённого движения.

### 7.4 Из Ball
Для Ball нет специальных transition exceptions сверх общего правила.

---

## 8. UI contract
### 8.1 Правый нижний угол экрана
UI form switching должен показывать:
- текущую форму;
- форму, на которую игрок перейдёт по `Q`;
- форму, на которую игрок перейдёт по `E`.

Это не просто индикатор текущего состояния, а инструмент предсказания следующего выбора.

### 8.2 Требование к читаемости
Игрок должен без паузы понимать:
- кто он сейчас;
- куда уйдёт следующий switch;
- что переключение формы вообще сейчас доступно.

---

## 9. Death / checkpoint interaction
### 9.1 После смерти
После смерти:
- игрок respawn'ится в форме `Ball`;
- позиция берётся из последнего checkpoint;
- form-specific состояния предыдущей формы не сохраняются.

### 9.2 Что обнуляется
После смерти обнуляются:
- trail / следы игрока;
- заряды;
- активные состояния форм;
- временные технические хвосты текущей формы.

---

## 10. Design-facing параметры
Все величины должны быть оформлены как параметры, а не как абстрактные захардкоженные числа.

Минимум параметров:
- длительность трансформации;
- lockout на повторный switch;
- длина / ритм переходной анимации;
- правила визуального fade / squash / stretch между формами;
- размеры / отступы UI form switching.

Параметры должны задаваться в игровых величинах:
- секунды;
- расстояния;
- скорости;
- индикаторные размеры.

---

## 11. Что документ сознательно не описывает
Этот документ не уходит в:
- реализацию анимации трансформации покадрово;
- конкретную scene/config wiring-структуру событий;
- кодовые детали блокировки switch;
- финальную визуальную стилистику UI.

Это будет решаться на implementation layer.

---

# The Form — Feature Doc: Ball

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`, `the_form_accepted_decisions_ru.md`
- Роль документа: зафиксировать полный игровой контракт формы Ball для нового Phaser-native / docs-first / prefab-by-code-first / TypeScript-first прототипа

---

## 2. Роль формы в прототипе
Ball — дефолтная форма игрока и форма респавна.

Это самая простая и наиболее читаемая форма прототипа. Она отвечает за:
- базовую мобильность;
- ускорение на земле;
- цепочку rebound-отскоков от поверхностей;
- читаемое ощущение динамики и ритма.

Ball должна быть понятной без сложного обучения, но при хорошем контроле позволять продвинутую игру через распрыгивание и rebound-chain.

---

## 3. Основная фантазия игрока
Игрок в форме Ball:
- быстро катится и разгоняется;
- чувствует контакт с поверхностью;
- может запускать серию точных отскоков;
- получает преимущество от хорошего тайминга, а не от накопления ресурса.

Ball не использует charges или отдельный ресурс.

---

## 4. Управление
### 4.1 Базовый input
- `A / D` — движение по горизонтали
- `Space` — обычный прыжок
- `K` — активная способность Ball
- `Q / E` — переключение формы

### 4.2 Общие правила, унаследованные от игрока
Для Ball обязательны:
- input buffer для прыжка / rebound-ввода;
- coyote time;
- air control;
- визуальный marker точки приложения;
- короткое состояние трансформации при смене формы.

### 4.3 Ability-кнопка
- `K` в форме Ball = ускорение

---

## 5. Базовое движение
### 5.1 Обычное движение
Ball — базовая grounded/airborne форма.

Обычное движение включает:
- ходьбу / катящееся перемещение по поверхности;
- обычный jump с пола;
- корректировку положения в воздухе.

### 5.2 Обычный прыжок
Обычный jump Ball:
- стартует от опоры;
- использует input buffer и coyote time;
- поддерживает dynamic jump height;
- работает как базовый прыжок уровня 1.

### 5.3 Dynamic jump height
Для обычного jump Ball:
- чем дольше удерживается `Space`, тем выше прыжок;
- рост высоты ограничен;
- профиль прыжка должен ощущаться как более быстрый в начале и более мягкий ближе к вершине.

---

## 6. Активная способность: ускорение
### 6.1 Суть способности
Ball по нажатию `K` получает ускорение на земле.

### 6.2 Контракт способности
Ускорение:
- работает только на земле;
- не работает в воздухе;
- не расходует ресурс;
- начинается как импульс;
- затем переходит в фазу более быстрого движения при удержании;
- после прекращения или завершения ускорения ощущается замедление / возврат к базовой скорости.

### 6.3 Design intent
Ускорение должно:
- усиливать ощущение инерции и скорости;
- помогать готовить выгодный вход в прыжок или rebound;
- не превращать форму в бесконтрольный снаряд.

---

## 7. Rebound-механика
### 7.1 Суть
Ball умеет отскакивать от пола, стен и потолка.

Это не полностью автоматический bounce по самому факту касания. Для rebound игрок должен подтвердить действие повторным нажатием `Space`, но с forgiving input logic.

### 7.2 Как запускается rebound
Базовый flow:
1. Ball находится в воздухе.
2. Ball входит в контакт с поверхностью, от которой rebound допустим.
3. Игрок нажимает `Space`.
4. Если нажатие попало в допустимое окно или было сделано чуть раньше и попало в buffer, запускается rebound.
5. Если rebound принят, срабатывает hit pause.
6. Далее Ball вылетает по rebound-траектории.

### 7.3 Buffer / forgiveness
Для rebound действует прощение неточного ввода:
- если игрок нажал `Space` чуть раньше допустимого момента,
- rebound всё равно должен стартовать, когда контакт станет валидным,
- при условии, что событие укладывается в настраиваемое buffer window.

### 7.4 Hit pause
Hit pause у Ball:
- срабатывает только если rebound действительно принят;
- не срабатывает при любом касании поверхности без успешного rebound;
- должен давать читаемое ощущение удара и подтверждения контакта.

Во время hit pause rebound не требует дополнительного выбора траектории: траектория определяется правилами геометрии поверхности.

### 7.5 Траектории rebound
#### От стен
При отскоке от вертикальных поверхностей:
- rebound идёт с upward assist;
- траектория корректируется немного вверх;
- цель: позволить игроку карабкаться rebound-прыжками между двумя близкими стенами.

#### От пола и потолка
При отскоке от горизонтальных поверхностей:
- используется правило «угол падения = углу отражения»;
- rebound должен сохранять читаемую геометрию отражения.

### 7.6 Уровни силы rebound
Ball использует 2 уровня прыжковой силы:
- уровень 1 — обычный jump с поверхности;
- уровень 2 — усиленный rebound после входа из состояния airborne.

Design intent:
- первый прыжок — базовый;
- второй и последующие rebound-прыжки дают ощущение распрыгивания;
- при хорошем исполнении игрок может строить бесконечную rebound-chain.

### 7.7 Ограничения rebound
- отдельного resource cap нет;
- искусственного ограничения длины цепочки нет;
- лимит задаётся только мастерством игрока, геометрией уровня и настройками окон/сил.

---

## 8. Marker точки приложения
Ball использует общий marker точки приложения.

Marker:
- всегда видим поверх фигуры;
- одинаковый по базовой логике для всех форм;
- плавно смещается внутри фигуры;
- имеет инерцию даже при keyboard input;
- возвращается в центр, когда игрок не даёт направление.

Для Ball marker нужен как:
- визуализация намерения игрока;
- часть общей системной идентичности прототипа;
- потенциальная база для будущих анимаций и реакции формы.

---

## 9. Взаимодействие с ветром
Wind zone влияет на Ball сильнее всех форм.

Эффект ветра:
- заметно меняет траекторию прыжка;
- влияет на падение;
- может усложнять rebound-входы;
- должен ощущаться сильнее, чем у Triangle и Square.

---

## 10. Взаимодействие с другими системами
### 10.1 Смерть / checkpoint
После смерти игрок:
- респавнится как Ball;
- появляется в сохранённой checkpoint-позиции;
- все состояния Ball сбрасываются;
- rebound-chain и boost-состояния обнуляются.

### 10.2 Смена формы
Смена формы:
- циклическая через `Q / E`;
- доступна везде;
- проходит через короткое состояние трансформации;
- новый хитбокс применяется в конце трансформации;
- если новая форма не помещается — трансформация отменяется.

При выходе из Ball:
- базовая скорость/направление движения сохраняются по общему правилу player system,
- если нет более сильного state-specific исключения.

---

## 11. UI
### 11.1 Нижний правый блок
Для Ball UI справа внизу показывает:
- текущую форму;
- соседние формы на `Q / E`.

### 11.2 Верхний UI
Для Ball в верхнем ресурсном UI на этапе прототипа ничего не отображается.

---

## 12. Параметры (design-facing)
Все численные значения должны быть вынесены в настраиваемые параметры в понятных единицах.

Ball как минимум требует параметры для:
- обычной скорости движения;
- ускорения / deceleration;
- jump высоты и времени удержания;
- coyote time;
- jump buffer;
- rebound buffer;
- hit pause;
- силы rebound уровня 1 и уровня 2;
- upward assist от стен;
- air control;
- веса формы для взаимодействия с ветром.

Параметры должны формулироваться в понятных design-терминах:
- секунды;
- расстояние;
- сила;
- скорость;
- вес.

---

## 13. Что не входит в этот документ
Этот feature doc не описывает:
- полную реализацию player core;
- технический способ scene/config wiring / TypeScript / Codex-slice orchestration-разбиения;
- общую систему камеры;
- общий doc по input;
- художественные VFX / анимации beyond prototype baseline.

---

## 14. Открытые места
На данный момент этот Ball-contract считается достаточно полным для прототипной документации.

Открытыми можно считать только будущие tuning-решения:
- точные значения скоростей;
- точные окна forgiving input;
- точную силу upward assist;
- желаемую визуальную драматургию hit pause.

# The Form — Feature Doc: Triangle

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`, `the_form_accepted_decisions_ru.md`
- Роль документа: зафиксировать полный игровой контракт формы Triangle для нового Phaser-native / docs-first / prefab-by-code-first / TypeScript-first прототипа

---

## 2. Роль формы в прототипе
Triangle — самая сложная и механически чувствительная форма прототипа.

Она отвечает за:
- управляемую ориентацию фигуры;
- freeze в воздухе;
- направленный dash;
- пробивание breakable-объектов;
- необычное ощущение прыжка через разворот.

Triangle — форма с наибольшим количеством нестандартного поведения. Именно поэтому она входит в prototyping order первой.

---

## 3. Основная фантазия игрока
Игрок в форме Triangle:
- управляет не только движением, но и направлением фигуры;
- чувствует ведущий угол;
- может зависнуть в воздухе, прицелиться и выполнить рывок;
- может врезаться в мир углом и буквально «вклиниваться» в геометрию;
- воспринимает каждую грань Triangle как потенциальную опору.

---

## 4. Геометрический контракт
### 4.1 Коллизия
Triangle:
- должен реально учитывать ориентацию;
- должен иметь коллизию, соответствующую форме треугольника;
- не должен вести себя как упрощённый box/circle hitbox под видом Triangle.

### 4.2 Ориентация
У Triangle есть ведущий угол.

Этот ведущий угол:
- определяет читаемую направленность формы;
- связан с visual marker;
- участвует в прыжке и dash-направлении.

### 4.3 Опорные поверхности
Каждая грань Triangle может выступать опорой.

Это означает:
- Triangle может лечь на грань;
- после взаимодействия с миром он должен встать на реальную грань;
- он не должен оставаться зависшим на угле или в случайном полунаклонённом состоянии как финальная stable pose.

---

## 5. Управление
### 5.1 Базовый input
- `W / A / S / D` — направление движения / ориентации
- `Space` — прыжок / freeze-flow
- `K` — dash
- `O` — восстановление charges
- `Q / E` — смена формы

### 5.2 Общие правила
Для Triangle обязательны:
- input buffer;
- coyote time там, где применим grounded jump;
- air control;
- visual marker точки приложения;
- короткое состояние трансформации при смене формы.

---

## 6. Базовый jump Triangle
### 6.1 Суть
У Triangle нет обычного jump в том же виде, что у Ball и Square.

Его jump — отдельная спец-механика, но построенная на тех же общих принципах платформинга.

### 6.2 Как ощущается jump
Когда Triangle прыгает:
- он резко разворачивается на месте;
- задаёт себе вращательное движение;
- затем отталкивается от поверхности.

Jump Triangle должен ощущаться как активное механическое отталкивание фигурой, а не как абстрактный вертикальный launch.

### 6.3 Jump-контракт
Jump Triangle:
- использует buffer и coyote time там, где это применимо;
- имеет фиксированную высоту / фиксированную силу;
- не использует dynamic jump height;
- зависит от ориентации фигуры и ведущего угла.

---

## 7. Freeze
### 7.1 Суть
Triangle может остановиться в воздухе по повторному нажатию `Space`.

### 7.2 Контракт freeze
Базовый flow:
1. Triangle прыгает / находится в воздухе.
2. Игрок повторно нажимает `Space`.
3. Triangle входит в состояние freeze.

Во freeze:
- Triangle зависает в воздухе;
- даёт игроку время на выбор направления;
- не тратит dash charge.

### 7.3 Поведение jump во freeze
Если Triangle уже вошёл во freeze:
- повторное нажатие `Space` не запускает новый jump;
- без дальнейшего действия Triangle может начать падать.

### 7.4 Выход из freeze
Freeze снимается:
- при переходе к dash;
- при смене формы;
- при выходе из состояния по внутренним правилам механики.

При смене формы из freeze:
- freeze снимается;
- ориентация Triangle сбрасывается;
- dash charge не тратится.

---

## 8. Dash
### 8.1 Суть
Dash — главная активная способность Triangle.

### 8.2 Цена способности
Dash тратит charge.

Freeze charge не тратит.

### 8.3 Charges
У Triangle:
- 3 charges;
- charges отображаются в UI как 3 отдельных сегмента / иконки;
- восстановление charges выполняется кнопкой `O`.

### 8.4 Восстановление charges
Контракт регена:
- выполняется только стоя на земле;
- запускается отдельной кнопкой `O`;
- восстановление не постепенное;
- оно происходит мгновенно после задержки и анимации.

### 8.5 Откуда можно сделать dash
Dash разрешён:
- с пола, если один из углов Triangle ориентирован валидно относительно поверхности;
- из воздуха после freeze;
- из воздуха без freeze.

### 8.6 Направление dash
Если dash запускается из воздуха без freeze:
- направление определяется текущей ориентацией Triangle;
- ведущий угол задаёт направление visual marker;
- dash не выбирается отдельно по новому marker input, а читается из текущей ориентации фигуры.

### 8.7 Поведение dash
Dash должен ощущаться как жёсткий, направленный рывок.

Во время dash Triangle:
- движется по заданной dash-траектории;
- использует свою реальную ориентацию;
- способен пробивать breakable-объекты.

---

## 9. Взаимодействие с объектами мира
### 9.1 Breakable-объекты
Breakable-объекты ломаются только от dash Triangle.

Ball и Square не имеют специального действия на эти объекты в первом прототипе.

### 9.2 Что происходит при пробитии
Если Triangle dash'ем попадает в breakable-объект:
- объект разрушается;
- область становится проходимой;
- проигрывается простая анимация / эффект;
- Triangle продолжает dash;
- допускается пробивание нескольких breakable-объектов подряд.

### 9.3 Непробиваемая поверхность
Если Triangle во время dash сталкивается с непробиваемой поверхностью:
- он застревает в ней углом;
- не пробивает её;
- не проходит сквозь неё.

После этого:
- по нажатию `Space` Triangle отпрыгивает по нормали поверхности;
- затем падает и должен прийти в устойчивое положение на грань.

---

## 10. Marker точки приложения
Triangle использует общий marker точки приложения, но именно у Triangle эта система особенно важна.

Marker:
- всегда видим;
- одинаков по базовой логике с другими формами;
- плавно смещается с инерцией;
- возвращается в центр при отсутствии ввода.

Для Triangle marker дополнительно:
- связан с ведущим углом;
- помогает игроку считывать ориентацию;
- визуально поддерживает логику прыжка и dash.

---

## 11. Смена формы
Смена формы доступна везде через `Q / E`.

Если игрок меняет форму во время Triangle-state:
- во freeze — freeze снимается, ориентация сбрасывается, charge не тратится;
- во время dash — новая форма продолжает движение по dash-вектору, но уже без спец-свойств dash Triangle;
- новая форма больше не ломает breakable-объекты только из-за сохранённого импульса.

Новый хитбокс включается в конце трансформации.
Если новая форма не помещается — трансформация отменяется.

---

## 12. Ветер
Wind zone влияет на Triangle:
- сильнее, чем на Square;
- слабее, чем на Ball.

Ветер:
- меняет траекторию прыжка и падения;
- во время dash замедляет Triangle;
- после завершения dash дальнейшее влияние идёт уже как на обычное airborne/grounded состояние Triangle.

---

## 13. Смерть / checkpoint
После смерти:
- игрок респавнится в форме Ball;
- charges Triangle восстанавливаются до полного значения;
- все Triangle-specific состояния сбрасываются.

Checkpoint сохраняет только позицию.

---

## 14. UI
### 14.1 Нижний правый блок
Показывает:
- текущую форму;
- соседние формы на `Q / E`.

### 14.2 Верхний UI
Для Triangle сверху отображаются:
- 3 отдельных сегмента / иконки charges.

---

## 15. Параметры (design-facing)
Triangle требует параметры как минимум для:
- длительности/свойств freeze;
- dash speed;
- dash distance / duration;
- jump силы;
- grounded orientation rules;
- charge restore delay;
- wind influence multiplier;
- веса формы;
- coyote time / buffer, где применимо.

Все параметры должны быть выражены в понятных единицах:
- секунды;
- расстояние;
- скорость;
- вес;
- количество charges.

---

## 16. Что не входит в документ
Документ не фиксирует:
- точные scene/config wiring-цепочки реализации;
- точную формулу вращения Triangle;
- художественные анимации beyond prototype baseline;
- постпрототипные special surfaces.

---

## 17. Открытые места
Открытыми для будущего тюнинга остаются:
- точное окно freeze;
- насколько резко Triangle должен доворачиваться;
- точная сила dash и поведение при входе в сложную геометрию;
- визуализация состояния «застрял углом».

# The Form — Feature Doc: Square

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`, `the_form_accepted_decisions_ru.md`
- Роль документа: зафиксировать полный игровой контракт формы Square для нового Phaser-native / docs-first / prefab-by-code-first / TypeScript-first прототипа

---

## 2. Роль формы в прототипе
Square — форма взаимодействия с поверхностями, удержания, маршрута и внешнего угла.

Она отвечает за:
- attach к валидным поверхностям;
- создание и расходование trail-ресурса;
- движение по поверхности;
- rollover через внешний угол;
- attach-jump с возвратом к trail;
- работу с движущимися attach-compatible объектами.

---

## 3. Основная фантазия игрока
Игрок в форме Square:
- прилипает к миру;
- оставляет на поверхности след своего маршрута;
- может двигаться по полу, стенам и потолку;
- «перекатывается» через внешние углы;
- временно отрывается от поверхности, но связан с ней как резинкой;
- сильнее чувствует маршрут и удержание, чем скорость.

---

## 4. Геометрический контракт
### 4.1 Коллизия
Square:
- всегда использует квадратный hitbox;
- при этом считается формой с реальным поворотом;
- поворот является частью канона, а не только визуальным эффектом.

### 4.2 Реальный поворот
Для Square важно, что:
- attach / rollover / позиционирование должны учитывать поворот;
- поведение не должно сводиться к «квадратному блоку без ориентации».

---

## 5. Управление
### 5.1 Базовый input
- `W / A / S / D` — движение
- `Space` — jump / attach-jump
- удержание `K` — attach
- `O` — regen trail
- `Q / E` — смена формы

### 5.2 Общие правила
Для Square обязательны:
- input buffer;
- coyote time;
- обычный jump;
- dynamic jump height для обычного jump;
- visual marker точки приложения;
- короткая трансформация при смене формы.

---

## 6. Базовое состояние без attach
Square вне attach ведёт себя как обычная игровая форма с возможностью:
- двигаться;
- прыгать;
- падать;
- переключаться в другие формы.

Обычный jump Square:
- использует buffer и coyote time;
- использует dynamic jump height;
- отличается от special attach-jump.

---

## 7. Attach
### 7.1 Суть
Attach — центральная механика Square.

Игрок удерживает `K`, чтобы прикрепиться к валидной поверхности.

### 7.2 Где attach допустим
Square может attach’иться к:
- полу;
- стенам;
- потолку;
- наклонным поверхностям;
- moving platforms;
- trigger platforms;
- специальным attach-compatible объектам.

Позже могут появиться поверхности, к которым attach невозможен, но в прототипе это ещё не вводится.

### 7.3 Attach и trail
Attach возможен:
- к валидной поверхности без готового trail;
- к поверхности, на которой trail уже существует.

Если attach начинается на поверхности без trail:
- trail начинает строиться с этого момента.

### 7.4 Если ресурс закончился
Если trail-resource закончился, находясь в attach:
- Square может стоять;
- Square не может строить новый trail.

---

## 8. Trail-resource
### 8.1 Суть ресурса
У Square нет charges.

Вместо этого у него есть trail-resource, который выражается как след на поверхностях и общий ресурс маршрута.

### 8.2 Как расходуется ресурс
Trail-resource расходуется:
- только по расстоянию;
- во время движения по поверхности.

Если Square стоит на trail без движения:
- ресурс не тратится.

### 8.3 Как хранится trail
Trail:
- глобальный;
- остаётся на поверхности, пока не будет собран обратно;
- может существовать на движущихся объектах;
- при движении объекта движется вместе с ним.

### 8.4 Перезапись trail
Если trail переписывается / регенится:
- сборка идёт глобально;
- направление сбора — от старого к новому.

---

## 9. Реген trail
### 9.1 Когда реген возможен
Реген trail возможен только вне attach.

### 9.2 Режимы регена
Square использует гибрид:
- автоматическое восстановление;
- ручное восстановление по `O`.

### 9.3 Ручной реген
При нажатии `O`:
- запускается режим регена;
- trail последовательно восстанавливается от старого к новому;
- если игрок начал новый attach, реген останавливается.

---

## 10. Attach-jump с возвратом
### 10.1 Суть
Находясь в attach и удерживая attach, Square может сделать специальный прыжок от trail.

### 10.2 Как запускается
Attach-jump запускается:
- кнопкой `Space`;
- пока удерживается attach (`K`).

### 10.3 Поведение
Во время attach-jump:
- Square отпрыгивает перпендикулярно поверхности;
- высота прыжка уменьшенная и фиксированная;
- до Square визуально сохраняется связь с trail;
- затем Square возвращается обратно к attach-точке.

### 10.4 Возврат
Возврат должен идти:
- не к старым мировым координатам;
- а к актуальной attach-точке / зоне, особенно если surface moved;
- визуально как натягивание связи / резинки.

### 10.5 Если attach отпущен
Если во время attach-jump игрок отпускает attach:
- Square отцепляется;
- дальше ведёт себя как обычная свободно падающая форма.

### 10.6 Работа с движущимися объектами
Attach-jump должен корректно работать, если Square привязан к движущемуся объекту:
- при возврате он должен прийти к актуальной поверхности объекта;
- он не должен пытаться вернуться в устаревшую стартовую мировую позицию;
- он не должен входить в объект при возврате.

---

## 11. Rollover через внешний угол
### 11.1 Суть
Square может переваливаться через внешний угол, оставаясь attached-to-surface сущностью.

### 11.2 Как стартует rollover
Базовый контракт:
1. Square уже в attach.
2. Игрок удерживает attach.
3. Игрок даёт движение вдоль attach-поверхности к внешнему краю.
4. При валидных условиях стартует rollover.

Отдельное дополнительное нажатие, кроме movement + hold attach, не требуется.

### 11.3 Attach к новой поверхности
Если rollover успешен:
- Square должен attach’иться к новой поверхности.

### 11.4 Неуспешный rollover
Если на новой поверхности attach невозможен:
- Square возвращается назад;
- строго по той же траектории;
- без дополнительных смещений.

### 11.5 Потолок
Attach к потолку и rollover в связке с потолком входят в полноценный канон прототипа.

---

## 12. Смена формы
Смена формы доступна везде.

Если игрок меняет форму во время Square attach-state:
- trail остаётся в мире;
- attach сразу сбрасывается;
- Square-specific состояния обнуляются;
- новая форма продолжает вести себя по своим правилам.

Новый hitbox включается в конце трансформации.
Если новая форма не помещается — трансформация отменяется.

---

## 13. Marker точки приложения
Square использует общий visual marker:
- всегда видим;
- одинаковый по базовой логике с другими формами;
- плавно двигается с инерцией;
- возвращается в центр без ввода.

Для Square marker помогает:
- считывать направление намерения игрока;
- в будущем поддерживать анимации и микрореакции формы.

---

## 14. Ветер
Wind zone влияет на Square слабее всех форм.

Если Square находится в обычном состоянии:
- ветер влияет на прыжок и падение;
- траектория меняется, но слабее, чем у Ball и Triangle.

Если Square находится в attach:
- ветер не сдувает его вообще.

---

## 15. Moving / trigger platforms
Для прототипа Square должен корректно работать с:
- moving platforms;
- trigger platforms.

Контракт:
- Square может attach’иться к ним, если они attach-compatible;
- trail может жить на них;
- trail двигается вместе с платформой/объектом.

---

## 16. Смерть / checkpoint
После смерти:
- игрок респавнится в форме Ball;
- trail / trail-resource сбрасываются и восстанавливаются до полного состояния;
- все Square-specific состояния обнуляются.

Checkpoint сохраняет только позицию.

---

## 17. UI
### 17.1 Нижний правый блок
Показывает:
- текущую форму;
- соседние формы на `Q / E`.

### 17.2 Верхний UI
Для Square сверху отображается:
- progress bar с сегментами trail-resource.

---

## 18. Параметры (design-facing)
Square требует параметры как минимум для:
- attach entry tolerance;
- attach move speed;
- обычного jump;
- dynamic jump height;
- attach-jump высоты и расстояния;
- trail maximum length/resource;
- расхода trail по дистанции;
- скорости регена;
- rollover window / tolerance;
- веса формы;
- влияния ветра вне attach.

Все параметры должны быть выражены в понятных design-единицах:
- секунды;
- расстояние;
- скорость;
- вес;
- длина trail.

---

## 19. Что не входит в документ
Документ не описывает:
- постпрототипные special no-attach surfaces;
- будущие advanced resource interactions между формами;
- полную техническую реализацию rollover;
- художественные эффекты beyond prototype baseline.

---

## 20. Открытые места
Как feature contract Square уже достаточно полон.

Открыты для будущего tuning-only слоя:
- точная длина trail-resource;
- точная скорость регена;
- точная feel-кривая attach-jump и возврата-резинки;
- точные rollover допуски и скорость.

# The Form — Feature Doc: Camera

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`
- Роль документа: зафиксировать игровой контракт камеры для первого прототипа

---

## 2. Назначение камеры
Камера в первом прототипе нужна не для кинематографичности, а для читаемого платформинга.

Её задачи:
- держать игрока в предсказуемой области экрана;
- помогать чтению геометрии и угроз;
- не дёргать игрока из-за мелких движений;
- не спорить с формами и не скрывать ключевые взаимодействия.

---

## 3. Основной контракт
### 3.1 Базовая роль
Камера следует за игроком, но не жёстко прилипает к нему центром.

### 3.2 Composition rule
Камера должна держать игрока ближе к нижне-центральной области кадра.

Это означает:
- в кадре должно оставаться больше видимого пространства впереди и выше игрока, чем ниже него;
- игрок не должен постоянно сидеть строго в геометрическом центре view.

### 3.3 Deadzone / frame rule
У камеры есть прямоугольная зона свободы (`deadzone / frame`):
- пока игрок движется внутри неё, камера не обязана реагировать;
- когда игрок упирается в границу зоны, камера начинает догонять его;
- поведение должно оставаться плавным и предсказуемым.

---

## 4. Поведение в первом прототипе
### 4.1 Что обязательно
Камера должна:
- следить за игроком;
- использовать frame/deadzone;
- сохранять нижне-центральный bias композиции;
- быть достаточно плавной для платформинга;
- корректно сопровождать переключение между формами.

### 4.2 Что не нужно на этом этапе
В первый прототип не входят:
- сложные кинематографические состояния;
- ветвистая state machine камеры;
- сюжетные пролёты;
- отдельные боевые / драматические режимы;
- большой camera framework.

---

## 5. Взаимодействие с формами
### 5.1 Общий принцип
Камера работает от единого `pf_player`, а не от трёх отдельных player-объектов.

### 5.2 Form switching
При смене формы камера:
- не теряет цель;
- не должна делать резких перескоков только из-за формы;
- должна продолжать сопровождать того же игрока с сохранением общего feel.

### 5.3 Ball
Для Ball камера должна оставаться достаточно читаемой при более быстрых участках, rebound и wall-bounce сценариях.

### 5.4 Triangle
Для Triangle камера не должна ломать чтение freeze / dash и столкновений с breakable / solid поверхностями.

### 5.5 Square
Для Square камера должна позволять читать:
- attach на стенах и потолке;
- перемещение по trail;
- rollover через внешний угол;
- attach-jump с возвратом.

---

## 6. Scene interaction
### 6.1 Test scene как основной reference
Первая test scene — основной reference для настройки камеры.

Камера должна быть удобной для чтения всех обязательных участков:
- ровный пол;
- стены;
- потолок;
- наклоны;
- узкий колодец;
- rollover-corner;
- breakable wall;
- moving / trigger platform;
- hazard / checkpoint / finish;
- wind zone.

### 6.2 Границы scene
Камера должна уважать границы scene и не показывать случайные технические пустоты за пределами игрового пространства.

---

## 7. Design-facing параметры
Все численные величины камеры должны быть параметризованы.

Минимум параметров:
- размеры deadzone/frame;
- горизонтальный и вертикальный bias;
- скорость догоняющего движения;
- сглаживание follow;
- пределы работы у scene bounds;
- возможные look-ahead смещения, если они понадобятся.

Параметры должны описываться в реальных величинах:
- пиксели / расстояния;
- секунды;
- скорости / коэффициенты сглаживания.

---

## 8. Debug / tuning expectations
Для камеры допустим простой debug/tuning слой, который помогает видеть:
- рамку свободы игрока;
- позицию target;
- реальные scene bounds;
- рабочие смещения.

Но полноценный debug framework не является частью scope первого прототипа.

---

## 9. Что документ сознательно не описывает
Документ не фиксирует:
- конкретную реализацию камеры в scene/config wiring или TypeScript;
- точные easing-функции;
- финальную художественную подачу переходов;
- поздние cinematic features.

# The Form — Feature Doc: Level Objects

## 1. Статус документа
- Статус: canonical draft
- Основание: `the_form_prototype_concept_ru.md`, `the_form_prototype_decisions_ru.md`
- Роль документа: зафиксировать минимальный канонический набор объектов мира для первого прототипа

---

## 2. Назначение слоя level objects
Первый прототип должен проверять не только формы сами по себе, но и то, как они читаются в окружении.

Поэтому level objects в test scene — это не декоративный набор, а обязательная часть проверки канона.

---

## 3. Обязательный состав test scene
В первой канонической test scene должны быть представлены:
- ровный пол;
- стены;
- потолок;
- наклонные поверхности;
- узкий колодец между двумя стенами;
- внешний угол для rollover Square;
- hazard;
- checkpoint;
- finish / exit;
- moving platform;
- trigger platform;
- wind zone;
- breakable wall / breakable object для Triangle.

---

## 4. Surface layer
### 4.1 Базовые поверхности
Базовые поверхности мира должны позволять проверять:
- обычное ground movement;
- wall / ceiling contact;
- наклоны;
- reflect / bounce сценарии Ball;
- attach и rollover сценарии Square;
- разные опорные грани Triangle.

### 4.2 Attach-compatible surfaces
Для первого прототипа attach-compatible считаются:
- пол;
- стены;
- потолок;
- наклоны;
- moving platforms;
- trigger platforms;
- специальные поверхности/объекты, предназначенные для attach.

В будущем могут появиться поверхности, к которым Square цепляться не может, но это не входит в канон первого прототипа.

---

## 5. Hazard
### 5.1 Назначение
Hazard нужен для проверки урона и checkpoint-loop.

### 5.2 Контракт
При контакте с hazard:
- игрок получает смерть;
- срабатывает death pause;
- затем игрок телепортируется на последний checkpoint;
- ресурсы и оставленные следы игрока сбрасываются.

### 5.3 Что не нужно
На первом прототипе hazard не требует:
- HP-системы;
- разных типов урона;
- resist / armor логики.

---

## 6. Checkpoint
### 6.1 Назначение
Checkpoint фиксирует точку возврата после смерти.

### 6.2 Контракт
Checkpoint сохраняет:
- только позицию.

Checkpoint не сохраняет:
- текущую форму;
- заряды;
- trail;
- временные состояния форм.

### 6.3 Respawn rule
После смерти игрок возвращается:
- в сохранённую позицию checkpoint;
- в форме `Ball`;
- с полным восстановлением ресурсов и очищенным temporary state.

---

## 7. Finish / Exit
### 7.1 Назначение
Finish / exit нужен, чтобы test scene ощущалась как минимальный вертикальный срез, а не как бесконечный песочничный стенд.

### 7.2 Контракт
Для первого прототипа достаточно простого контракта:
- игрок достиг триггера выхода;
- игра фиксирует, что scene пройдена;
- сложная metagame-логика не требуется.

---

## 8. Moving platform
### 8.1 Назначение
Moving platform проверяет:
- устойчивость опорного движения;
- перенос игрока движущейся поверхностью;
- работу форм на динамическом основании;
- attach / trail взаимодействия Square с движущимся объектом.

### 8.2 Контракт
Moving platform в первом прототипе должна:
- возить игрока как опорная поверхность;
- корректно работать с Ball / Triangle / Square;
- позволять Square attach'иться к себе, если поверхность attach-compatible;
- позволять trail жить на себе и двигаться вместе с платформой.

### 8.3 Scope rule
На первом шаге не нужен сложный класс транспортов или общая система всех возможных кинематических платформ.

---

## 9. overlap zone platform
### 9.1 Назначение
overlap zone platform нужна как отдельный случай управляемого объекта уровня, который двигается не сам по себе, а активируется событием / триггером.

### 9.2 Контракт
overlap zone platform должна:
- запускаться по каноническому триггеру;
- после запуска двигаться по заданному поведению;
- выступать опорной поверхностью;
- быть attach-compatible для Square в первом прототипе;
- поддерживать trail на своей поверхности.

---

## 10. Wind zone
### 10.1 Назначение
Wind zone нужна для проверки того, как формы по-разному читаются под внешним воздействием среды.

### 10.2 Контракт по формам
Wind zone влияет на все формы, но не одинаково:
- `Ball` сдувает сильнее всего;
- `Triangle` — сильнее, чем Square, но слабее, чем Ball;
- `Square` сдувает слабее всего;
- `Square` в attach wind не сдувает вовсе.

### 10.3 Влияние на движение
Wind zone должна менять траекторию:
- прыжка;
- падения;
- общего движения в воздухе.

Для Triangle:
- active dash замедляется ветром;
- после окончания dash действует обычное влияние ветра по правилам текущей формы/состояния.

---

## 11. Breakable object / wall
### 11.1 Назначение
Breakable-объекты проверяют уникальную ценность Triangle.

### 11.2 Контракт
Breakable surface:
- ломается только от dash Triangle;
- не имеет специальной уязвимости к Ball или Square;
- после разрушения исчезает;
- область становится проходимой;
- может проигрывать простой эффект / простую анимацию разрушения.

### 11.3 Chain rule
Triangle может пробивать несколько breakable-объектов подряд, если сохраняет валидный dash.

---

## 12. Геометрические требования к test scene
Test scene должна включать такие зоны, где можно проверить:
- Ball wall-bounce вверх между двумя близкими стенами;
- Triangle dash с пола;
- Triangle freeze + dash из воздуха;
- Triangle удар в breakable и в non-breakable поверхность;
- Square attach на полу / стене / потолке / наклоне;
- Square rollover через внешний угол;
- Square attach-jump с возвратом;
- Square на движущемся объекте;
- поведение форм в wind zone;
- death / checkpoint / finish loop.

---

## 13. Что документ сознательно не описывает
Документ не уходит в:
- финальный art-pass объектов;
- звуковую систему;
- сложные классы интерактивных предметов;
- metaprogression;
- поздние дизайнерские типы hazards и interactables.
